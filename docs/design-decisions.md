# 설계 결정 기록

`docs/audit.md` 가 **구현**의 결함을, 설계 감사서가 **설계 문서 자체**의 결함과 상용 대비
격차를 다뤘다. 그 두 문서는 **검토 입력**이고, 이 문서가 **결정**이다.

감사서의 보강안은 "넣으면 좋을 것" 의 목록이지 채택이 아니다. 판정을 안 남기면 다음 사람이
같은 항목을 처음부터 다시 저울질하고, 그 사이에 **기각한 이유가 사라진다** — 이 제품에서
"안 하는 것" 은 대부분 근거가 있는 결정이지 미구현이 아니다.

판정은 넷이다:

| 판정 | 뜻 |
|---|---|
| **채택** | 설계로 확정. 구현 라운드가 정해져 있다 |
| **조건부 채택** | 방향은 확정. 범위나 시점이 선행 조건에 걸려 있다 |
| **보류** | 지금 안 한다. **해제 조건을 함께 적는다** — 조건 없는 보류는 망각이다 |
| **기각** | 이 제품의 원칙과 상충한다. 근거를 남겨 재론 비용을 줄인다 |

"채택" 은 결정이지 구현이 아니다. **어디까지 구현됐는지는 각 항목의 `현재` 줄이 말한다** —
결정과 구현을 한 문장으로 뭉치면 "채택했다" 가 "됐다" 로 읽히고, 부채가 조용히 사라진다.

## 1. 설계 결함 (D1–D15)

### D1 / G1. 출력(응답) 축 — **채택 · 구현 완료(1단)**

제품의 한 문장은 "나가는 프롬프트에서 개인정보를 걸러낸다" 인데, 순서 계약·2단 판정·
경계별 마스킹·원문 암호화·보존 기간이 **전부 입력에만** 있었다. `jobs.response` 는 평문
`TEXT` 였고, 마스킹도 암호화도 별도 보존 기간도 없었다.

응답에 민감정보가 실리는 경로는 가정이 아니라 실재한다 — 요약·추출 작업의 산출물 자체가
개인정보이거나, 인젝션이 시스템 프롬프트를 응답으로 끌어내거나, 모델이 마스킹되지 않은
문맥을 재구성한다.

**초크포인트가 이미 있었다.** `scheduler._succeed()` 가 `jobs.response` 를 쓰는 **유일한
지점**이다. 입력 축에서 `pipeline.py` 가 잡 생성의 유일한 경로인 것과 같은 구조이고,
그래서 출력 가드는 새 배관이 아니라 **한 함수 안의 추가**였다.

`현재`: **구현됐다.** `_succeed()` 안에서 검사 → 봉인 → 저장이 한 덩어리로 돈다:

- 입력과 같은 1단 규칙(베이스라인 + 테넌트 로케일 팩 + 테넌트 추가 규칙)을 응답에 적용
- 마스킹본을 `jobs.response` 에, 원문은 `response_cipher` 에 봉인(AAD 는 프롬프트와 **다른**
  `resp:{tenant}:{job}` — 같으면 필드 간 이식이 성립한다)
- 보존은 `raw_prompt_retention_days` 같은 축, 열람은 같은 단건 API + 감사(무엇을 열었는지까지)
- 출력에서 `block` 은 `full` 로 강등 — 추론이 끝난 뒤라 응답을 통째로 버리면 소비자는
  비용만 내고 아무것도 못 받는다
- 초크포인트 불변식은 `test_only_the_scheduler_writes_the_response` 가 지킨다

**남은 것**: 출력 2단(LLM 맥락 분류). 응답마다 추론이 한 번 더 늘어나므로 지연·비용을
실측한 뒤에 붙인다 — 켜 놓고 나중에 재는 것은 순서가 거꾸로다. 부채 표에 명시.

설계 근거 전문은 [architecture.md](architecture.md) §7.1-1.

### D2. "YAML 은 시드, DB 가 권위" 가 데이터 모델에 없었다 — **채택 · 이번 라운드**

원칙은 세 곳에 선언돼 있는데 그 권위를 담을 테이블이 설계에 없었다. 그 간극이 구현 감사
HIGH 2건(H4 죽은 오버라이드 · H5 노드 소실)의 뿌리다.

`현재`: **구현 완료.** `nodes` 테이블 + `role_overrides` 적용 지점(`roles.RoleResolver`).
문서만 없었다 → `docs/architecture.md` §10 에 데이터 모델과 적재 순서를 명시했다.

### D3. 신뢰 경계 표가 배포 기본값과 어긋났다 — **채택 · 이번 라운드**

`docs/topology.md` §2 는 "`/v1/admin/*` 을 404 로 숨김" 이라고 적었다. 세 가지가 틀렸다:

1. `/v1/admin/*` 은 **테넌트 관리자의 API 다**(`app/main.py` 의 `tenant_*` 라우트군).
   경계에서 막으면 테넌트 관리자가 자기 관제 UI 를 못 쓴다. 숨겨야 하는 것은
   플랫폼 관리 면 `/v1/platform/*` 이다.
2. 프록시는 `--profile tls` **옵트인**이라 기본 배포에 없다.
3. 그 차단을 하는 설정 파일이 **저장소에 없었다.** 표가 제품의 통제처럼 읽히는데 실제로는
   설치처 숙제였다.

**결정**: (b) 안 — 차단 대상을 `/v1/platform/*` 으로 정정하고 **그 설정을 번들에 담는다.**
(a) 안(관리 면 별도 리스너 바인드)은 더 강하지만 컨테이너·문서·부트스트랩이 전부 2벌이
되므로 Scale 프로파일로 미룬다.

`현재`: `tls/nginx.conf` 를 번들에 추가했다. topology §2 를 **"제품이 강제하는 것"** 과
**"설치처 전제"** 두 축으로 다시 썼다.

### D4 / G5. 키 회전 설계가 없다 — **채택 · 구현 완료**

마스터 KEK 회전 절차가 없었다. re-wrap 은 **DEK 래핑만 교체하면 되므로 암호문 재암호화
없이 가능**한데 그 사실조차 어디에도 없었다 — 유출 의심 상황에서 그것을 그 자리에서
알아내는 것은 최악의 시점이다.

Shamir 분할·이중 봉투는 **기각**한다: 설치처 운영자가 조각을 잃으면 복구가 더 어려워지고,
"KEK 는 백업과 다른 곳에" 라는 단순한 규칙이 이 제품의 실제 위협(호스트 분실·백업 유출)을
이미 덮는다. 복잡한 키 의식은 지키지 않으면 없는 것과 같다.

**해제 조건이었던 것**: "KEK 유출 대응 절차(런북)를 쓰는 시점. 그때 CLI + 감사와 함께
낸다." → `docs/runbook-key-compromise.md` · `lcc rotate-kek` · `rotate_master_kek`
감사 기록으로 셋 다 냈다.

#### 설계에서 정한 것

**없앨 수 없는 창을 두 키가 다 있는 창으로 만든다.** DB 커밋과 키 파일 교체는 서로 다른
저장소에 대한 쓰기라 한 트랜잭션으로 못 묶는다. 그래서 새 키를 `master.key.new` 로 **먼저**
쓰고, 커밋하고, 그 뒤에 파일을 교체한다. 어디서 죽어도 두 키가 디스크에 있고, 남아 있는
`master.key.new` 자체가 중단의 증거다.

**중단의 어느 쪽인지를 사람에게 묻지 않는다.** "DB 가 새 키로 감싸여 있다면 이렇게
하세요" 라고만 적으면 그 판단을 유출 대응 중인 운영자에게 떠넘기는 것이고, 틀리면 어떤
키로도 못 여는 상태가 된다. `doctor` 가 무대에 오른 키로 실제 DEK 를 열어 보고 판정한다.

**무대의 키를 치우는 것은 DB 를 안 건드렸음이 확실할 때만.** 치우는 이유는 진단이 있지도
않은 중단을 보고하지 않게 하려는 편의뿐인데, 커밋됐는지 모르는 채 치우면 복구 수단을
없앤다. 그래서 순수 계산 구간만 정리 대상이고, 저장소를 부른 뒤부터는 무슨 일이 나든
둘 다 남긴다.

**진단이 키를 실제로 검증한다.** `doctor` 는 그동안 "마스터 KEK 있음" 만 말하고 그 키가
DEK 를 여는지는 안 봤다. 키를 잘못 바꾼 설치처는 사용자가 원문을 열려는 순간에야 알게
되고, 증상이 "복호화 실패" 뿐이라 원인을 찾는 데 한참 걸린다.

#### DEK 회전은 **기각**한다

D4 는 "DEK 회전을 re-wrap 과 같은 라운드에서 함께 정의한다" 고 했다. 정의한 결과는
"만들지 않는다" 이고, 근거는 위협 모델이다:

- DEK 는 평문으로 프로세스 밖에 나가지 않는다 → **DEK 만 유출되는 경로가 없다.**
- KEK 만 샜다면 공격자는 DB 를 못 가졌으므로 DEK 에 닿지 못한다 → **re-wrap 으로 충분.**
- KEK + DB 가 샜다면 공격자가 암호문 사본을 오프라인으로 들고 있다 → **DEK 를 바꿔도
  이미 읽힌 것을 못 되돌린다.**

DEK 교체가 실제로 하는 일은 그 테넌트의 기존 암호문을 못 열게 만드는 것(crypto-shredding)
이고, 그것이 필요한 상황은 "보관 원문을 지운다" 이며 그 경로는 **이미 있다** — 테넌트
파기(`purged_at` + `dek_wrapped = NULL`). 같은 일을 하는 두 번째 명령을 만들면 둘 중
하나는 언젠가 잘못된 상황에서 불린다. 보관 원문의 수명은 `raw_prompt_retention_days`
(기본 7일)가 조절한다.

### D5. 클라우드 API 키의 소유 축이 모순 — **채택 · 이번 라운드**

`docs/deployment.md` §6 은 "클라우드 API 키 — **테넌트별**, KEK 로 래핑" 이라고 적었지만,
노드 모델은 플랫폼 공유 풀이고 키는 `api_key_env`(환경변수 참조)다. 노드 1개 = 키 1개이므로
테넌트별 키는 현 노드 모델과 **구조적으로 양립하지 않는다.**

**결정**: 현 구현(플랫폼 단위 env 참조)을 설계로 승인하고 §6 을 정정한다.
테넌트별 키를 넣으려면 노드-키 바인딩 모델부터 다시 정의해야 하고, 그것은
`tenant_affinity` 전용 노드로 이미 부분적으로 표현된다(전용 노드 = 전용 키).

**대가를 함께 적는다**: 클라우드 비용의 **프로바이더 청구서 상 귀속이 플랫폼 단위**다.
테넌트별 귀속은 이 제품의 `usage` 로만 성립하고 프로바이더 콘솔에서는 안 보인다.
키 폐기 단위도 플랫폼이다 — 한 테넌트 때문에 키를 갈면 전 테넌트가 영향을 받는다.
→ 부채 표에 명시.

### D6. 다중 프로세스 구성이 "지원한다면서 설계되지 않았다" — **채택 · 이번 라운드**

`store.py` 독스트링은 "API 워커 N 개 + 스케줄러 싱글턴" 을 **지원한다고 단언**했는데,
그 구성이 요구하는 동시성 계약(claim 원자성 · 상태 선행조건 · 쓰기 트랜잭션 규율)이
설계 어디에도 없었다.

**결정**: 다중 워커를 **지원 구성으로 승격**하고 계약을 명시한다(사용자 확정).
계약 본문은 `docs/architecture.md` §11 에 있다. 승격의 조건은 **한계를 같이 적는 것**이다:

- `claim_queued()` 는 이름과 달리 **claim 하지 않는다.** 상태 전이 없는 순수 SELECT 이고,
  실제 직렬화는 `_try_dispatch` 의 CAS 가 한다. 이름이 계약을 과장하고 있다.
- `cluster.place()` 의 슬롯·메모리 예약은 **프로세스 메모리 + `threading.Lock`** 이었다.
  비동기 경로는 스케줄러가 싱글턴이라 안전하지만, **동기 경로 두 곳**(`/v1/embed` 과
  가드 2단 분류)은 API 워커에서 `place()` 를 부른다 → 워커 N 개면 슬롯 장부가 N 벌이다.
  → **해소됐다.** 아래 D6-b.
- 다중 프로세스 경합 테스트가 **없다.** → **해소됐다**(`tests/test_multiprocess.py`).
  진짜 프로세스 4개로 재 보니 CAS 는 정확히 한 번 이기고 `SQLITE_BUSY` 도 안 났다.

이 셋을 안 적고 승격하면 D6 이 지적한 실패(검증 안 된 것을 문서가 단언)를 그대로 반복한다.

### D6-b. 슬롯 장부를 DB 로 — **채택 · 구현 완료**

승격의 대가로 적어 둔 한계 중 하나가 **정합성 결함**이었다. "지원 구성" 이라고 선언한
형태에서 `max_concurrent=1` 로 잡아 둔 단일 GPU 노드에 워커 수만큼 요청이 올라가면
OOM 이다. 선언을 참으로 만드는 것이 먼저다.

**결정**: 점유를 `node_leases` 테이블로 옮긴다. 슬롯 하나 = 행 하나.

근거는 이미 이 저장소 안에 있었다 — 레이트리밋 카운터가 같은 이유로 DB 에 있다
(`store.py` 의 `rate_counters` 주석: *"워커를 N개 띄우면 각자 자기 카운터를 갖게 되어
실효 한도가 N배가 된다. 한도가 조용히 곱해지는 것은 제품에서 버그다"*). 슬롯도 한도다.

설계에서 정한 것 셋:

1. **확정은 트랜잭션 안에서.** 스냅샷으로 후보를 거르고 순위를 매기되, 커밋은
   `try_acquire_node_lease()` 가 쓰기 트랜잭션 안에서 용량을 재확인하며 한다.
   멱등성 키에서 배운 것과 같다 — "먼저 조회하고 없으면 삽입" 은 다중 워커에서 진다.
2. **`NodeState.running` 필드를 지운다.** 남겨 두면 언젠가 누군가 낡은 쪽을 읽는다.
   점유는 필드가 아니라 질의다(`Cluster.occupancy()`).
3. **리스에 만료를 단다.** 만료가 없으면 DB 장부가 인메모리 장부보다 **나쁘다** —
   인메모리 예약은 워커가 죽으면 같이 사라지지만 행은 안 사라진다.

**대가**: 배치마다 쓰기 트랜잭션이 하나 늘고, SQLite 는 라이터를 직렬화한다.
실측 **0.15ms**(`app.loadtest` 의 `place_release`, 6,600/초)로 클러스터 상한
2.7 job/초 대비 서너 자릿수 여유다. 병목이 아니다.

**남는 한계**: 죽은 워커의 슬롯은 만료(역할 `timeout` + 30초)까지 잡혀 있다.
정합성은 지켜지고 가용성만 늦으므로, 초과 구독과 맞바꿀 값어치가 있다.

### D7 / G3. 멱등성 키가 API 계약에 없다 — **채택 · 구현 완료**

`wait` + pending 모델은 타임아웃-재시도를 오히려 장려하므로 이 공백이 더 아프다.
metered 경로에서는 이중 제출이 곧 이중 과금이다.

설계는 확정한다: `Idempotency-Key` 헤더, **테넌트+서비스 스코프**, TTL 창 내 같은 키는
기존 잡을 반환. 잡 테이블의 유니크 컬럼 하나로 끝난다.

`현재`: **구현됐다.** `Idempotency-Key` 헤더, (테넌트, 서비스) 스코프, 24시간 TTL.

해제 조건("중복 잡을 만든 첫 사례 또는 metered 티어를 켜는 시점")보다 먼저 냈다 —
비용이 유일 인덱스 하나였고, 마침 다중 워커 계약을 확정한 직후라 **"유일성은 DB 가
지킨다" 를 같은 라운드에서 검증할 수 있었기** 때문이다. `tests/test_multiprocess.py`
가 진짜 프로세스 4개로 그것을 잰다.

**한계 — 페이로드를 비교하지 않는다.** 같은 키로 다른 프롬프트를 보내면 첫 요청의
잡이 돌아온다. 비교하려면 프롬프트 지문이 필요한데 원문 해싱은 C8 이 금지한 그것이고
(탐색 공간이 좁은 값은 전수조사로 복원된다), 마스킹 후 해싱하려면 가드를 먼저 돌려야
해서 재시도마다 2단 분류가 다시 돈다. 계약과 부채 표에 명시했다.

`/v1/embed` 는 대상이 아니다 — 동기 경로라 pending 상태가 없고 수명주기가 다르다.

설계 근거 전문은 [architecture.md](architecture.md) §11 아래 "멱등성".

### D8. 한도 축이 요청 수와 달러뿐 — **조건부 채택 · 계측 완료**

무료(internal) 경로는 달러가 0 이라, 200KB 프롬프트 1건과 1KB 프롬프트 1건이 같은 1건이다.
대형 프롬프트를 던지는 테넌트가 건수 한도를 지키면서 클러스터를 잠식할 수 있다.

**조건부인 이유**: 토큰 상한의 값을 지금 정할 근거가 없다. `estimate_input_tokens()` 로
추정 토큰은 이미 계산하고 있으므로 **집계와 노출이 먼저**다 — 테넌트별 TPM 을 관제 UI 와
`/metrics` 에 먼저 띄우고, 실측 분포를 본 뒤 상한을 건다. 값을 모르는 채 건 한도는
오탐 규칙과 같은 운명을 맞는다(관리자가 꺼버린다).

`현재`: **계측이 됐다.** `store.token_rate()` 를 `/metrics`(전 테넌트 합계, 테넌트
라벨 없음)와 `GET /v1/admin/usage`(테넌트별)에 띄운다. **한도는 걸지 않았다** —
그것이 이 항목이 "조건부" 인 이유 그대로다.

**해제 조건**: 설치처의 실측 분포. 그것을 보고 상한 값을 정한다.
배치 스캔 공정성 가중치에 토큰 크기를 반영하는 것은 그다음이다.

### D9 / G4. 분류기의 적대적 입력 내성 — **채택 · 구현 완료**

2단은 사용자 텍스트를 LLM 에게 보여주고 "민감한가" 를 묻는다. 그 텍스트가 분류기를 향한
지시를 담으면 판정이 뒤집힐 수 있다 — **가드가 가드를 뚫는 입력에 무방비다.**

`현재`: **구현됐다.** 방어가 세 겹이고 각 겹이 다른 지점에서 성립한다:

1. **구조** — 자료를 울타리에 넣고 지시를 자료 앞뒤에 둔다. 울타리 토큰은 인스턴스마다
   다른 비밀에서 HMAC 으로 나오므로 공격자가 닫을 수 없다. 소스 상수나 텍스트 해시로는
   부족하다 — 오픈소스 제품에서는 공격자도 그 값을 계산할 수 있다.
2. **이탈 탐지(카나리아)** — 출력에 카나리아가 없으면 **판정이 아니라 실패**로 올려
   `on_classifier_error` 를 태운다. 인젝션이 성공하면 모델이 우리 형식을 버리므로
   그것이 곧 이탈 신호이고, "해당 맥락 없음" 으로 읽으면 공격이 노린 결과를 준다.
3. **시도 탐지** — `injection` 팩(로케일 무관 `always_on`). 제어 토큰·구조 위조는
   오탐이 거의 없어 `full`, 지시 무효화·프롬프트 유출 시도는 `audit` 로 시작한다.

설계 근거 전문은 [architecture.md](architecture.md) §7.2-1.

**남은 것**: 경량 전용 분류기(Prompt Guard 급). 휴리스틱 팩은 아는 문장만 잡으므로
새로운 표현은 놓친다 — 구조적 방어가 표현과 무관하게 도는 것과 대조된다. 전용 분류기는
**분류 모델 등록 게이트(C7)를 그대로 통과해야 한다.** 부채 표에 명시.

`always_on` 이 죽은 플래그였던 것도 이 라운드에서 함께 고쳤다 — `rules_for_locales` 가
`"common"` 을 이름으로 하드코딩해서, YAML 에 `always_on: true` 를 단 팩이 조용히 안
켜졌다. 인젝션 팩이 정확히 그런 팩이라 먼저 고쳐야 했다.

### D10. 감사 로그의 무결성·보존 — **부분 채택 · 나머지 보류**

`현재`: **보존은 구현됐다** — `AUDIT_RETENTION_DAYS = 365`, `purge_expired` 가 정리한다.

**보류**: 순차 해시 체인(행마다 이전 행 해시)과 감사 내보내기 경로. 해시 체인은
"조작할 수 없다" 를 만드는 장치지, "조작하면 드러난다" 이상은 못 한다 — DB 를 쓸 수 있는
공격자는 체인 전체를 다시 계산할 수 있다. 진짜 무결성은 **외부로 밀어내는 것**(SIEM·
append-only 스토리지)에서 나오므로, 체인만 넣고 컴플라이언스를 주장하면 과장이다.

**해제 조건**: 감사 무결성이 계약서에 들어가는 첫 거래. 그때 체인 + 외부 내보내기를
한 묶음으로 낸다.

### D11. 장애 반경 표가 목표인지 현재 상태인지 구분이 없다 — **채택 · 이번 라운드**

표의 각 행이 **설계 보증**인지 **희망**인지 표기가 없어, 구현이 표를 배신해도 드러나지
않았다. 실제로 배신하고 있었다 — "재기동 시 복구" 는 노드가 영속화되지 않던 시점(H5)에는
성립하지 않았다.

`현재`: `docs/topology.md` §7 을 검증 가능한 문장으로 다시 쓰고, **각 행에 그것을 고정하는
테스트 이름을 적었다.** 표만 고치면 같은 문제가 반복되므로 **표의 모든 행이 실재하는
테스트를 지목하는지 검사하는 테스트**를 함께 붙였다(`tests/test_blast_radius.py`).

### D12. 관리자 신원 축이 없다 — **채택(부채 등재) · 구현 보류**

모든 신원이 Bearer 토큰 하나다. IdP 연동·MFA·관리 세션 만료·권한 상승 재인증이 설계에
없고, **"하지 않는 것" 목록에도 없었다** — 즉 검토 자체가 누락됐다. 테넌트 관리자가
사람이라면 그 사람의 퇴사는 IdP 에서 일어나는데, 이 제품의 토큰은 그것과 이어질 길이 없다.

`현재`: 프로토타입 범위임을 인정하고 **부채 표에 명시**했다. 제품화 시 OIDC(관리 UI 한정)
가 로드맵 1순위다 — API 토큰은 그대로 두고 사람이 쓰는 면만 IdP 에 태우는 것이
파급이 가장 작다.

### D13. 완료 통지의 공백이 내부 폴링으로 전가됐다 — **채택 · 구현 완료**

밖으로의 통지(웹훅)를 기각한 근거는 문서화돼 있는데, **안에서의 통지**를 설계하지 않아
`wait` 이 프로세스 내부 DB 폴링으로 귀결됐다. 같은 프로세스 안에서는 SSRF 도 인증도
문제가 아니다.

`현재`: **구현됐다.** `app/completion.py` 의 `CompletionSignal` 을 파이프라인과
스케줄러가 **같은 객체로 공유**하고, 종결 전이에서 `done()` 을 부른다.

**폴링을 없애지 않았다.** D6 승격 때문이다 — 잡을 끝내는 프로세스(스케줄러)와 `wait`
하는 프로세스(API 워커)가 다르고 `asyncio.Event` 는 프로세스를 넘지 못한다. 그래서
신호는 `asyncio.sleep(interval)` 자리를 대신할 뿐이고, 신호가 안 오면 정확히 예전만큼
잔다. 최적화는 틀려도 느려질 뿐이어야 한다.

설계 근거 전문은 [architecture.md](architecture.md) §11 아래 "완료 통지".

**구현 중 하나 걸렸다**: 등록·해제를 `@contextlib.contextmanager` 로 짝지었더니,
예외가 그 블록을 지날 때 파이썬이 `gen.throw(exc)` 로 예외의 `__traceback__` 을
건드리는데 이 저장소의 `ApiError` 가 **동결 데이터클래스**라 `FrozenInstanceError` 로
터졌다 — 대기 루프 안에서 `job_not_found` 를 던지는 정상 경로가 통째로 깨졌다.
테넌트 격리 테스트가 잡았고, 클래스 기반 `__exit__` 로 바꿔 해소했다.

### D14. 청구 기간과 보존 기간이 같은 상수에 묶여 있다 — **채택 · 완료**

`현재`: **구조로 강제되고 있다.** `store.purge_expired` 가
`usage_cutoff = min(job_cutoff, now - BUDGET_WINDOW_DAYS * 86400)` 으로 자른다 —
잡 보존을 14일로 줄여도 usage 는 예산 창 30일만큼 남는다. 근거를
`docs/architecture.md` §12 에 기록했다.

달력 월 옵션은 **보류.** 해제 조건: 설치처 회계가 롤링 30일을 거부하는 첫 사례.

### D15. 경계 모델이 이분법 — **채택(설계 노트) · 구현 보류**

`internal | external` 2값은 출발점으로 옳지만 "EU 리전만" · "국내 IDC 만" ·
"ZDR 계약 프로바이더만" 을 표현할 수 없다.

**지금 바꾸지 않는 이유**: 2값 위에서 배치 필터·가드 등급 매핑·스냅샷 교집합의 테스트가
성립하고 있고, 요구가 실재하기 전에 일반화하면 **검증되지 않은 자유도**가 늘어난다.
경계는 이 제품에서 가장 안전이 걸린 축이라 그 자유도의 대가가 크다.

**일반화 경로는 남긴다** — `docs/architecture.md` §13. 요지: 경계를 열거형 2값이 아니라
**순서 있는 신뢰 등급**으로 보면 값 추가만으로 확장된다. 가드 등급 매핑이 이미 경계
*이름* 기준이므로 새 이름을 넣는 것 자체는 데이터 변경이다. 손대야 하는 곳은
"안전은 교집합" 을 구현한 세 지점뿐이다.

### G2. 유니코드 정규화 + 시크릿 탐지 팩 — **구현 완료 · 일부 기각**

`현재`: 정규화는 **구현됐다.** `guard.normalize_for_match()` 가 NFKC + 비가시 문자
스트리핑을 하고, **원문은 보존한 채 검사만 정규화본으로** 하며 스팬을 원문 좌표로
되돌리는 인덱스 맵을 함께 돌려준다. 전각 하이픈·NBSP 구분자·zero-width 우회가 막힌다.

`현재`: 시크릿 팩도 **구현됐다** — `secrets` 팩(로케일 무관 `always_on`), 벤더 접두사 ·
PEM 개인키 · 대입 문맥 세 규칙. 전부 `full` 이고, 출력 축에도 같은 규칙이 걸리므로
**모델이 문맥의 키를 응답에 되풀이하는 경로**가 막힌다.

**"고엔트로피 문자열" 은 기각한다.** 감사서가 제안한 절반인데, 실측하면 섀넌 엔트로피는
진짜 시크릿과 정상 문자열을 가르지 못한다 — `token_hex` 시크릿(3.635)이 UUID(3.663)보다
낮고, base64 로 인코딩한 영문(4.930)이 진짜 base64 시크릿(4.539)보다 높다. 임계를 어디에
두든 진짜 키를 놓치거나 모든 git SHA 를 잡는다.

대신 신호를 **접두사와 문맥**에서 얻는다. `credential_shape` 체크섬이 자리표시자
(`YOUR_KEY_HERE` · `changeme-*` · `password_hash`)를 걸러내고, 그 오탐률을 34건짜리
회귀 코퍼스로 잰다(0%, 승격 게이트 임계 2%).

기각 근거는 `tests/test_secrets.py::test_entropy_cannot_separate_secrets` 가 숫자로
고정한다 — 나중에 "엔트로피로 하면 되지 않나" 를 다시 물을 때 재측정 비용을 없애기
위해서다. 설계 근거 전문은 [architecture.md](architecture.md) §7.2-1 아래.

### G6. OpenAI 호환 어댑터 — **채택 · 보류**

원형 그대로는 "역할 이름이 계약, 모델명 하드코딩 금지" 와 정면충돌한다. 채택하는 형태는
하나뿐이다: **`model` 필드에 역할 이름을 받는** `/v1/chat/completions`, 가드·배치·비용은
동일 파이프라인 통과, 스트리밍 미지원 유지.

**해제 조건**: 설치처가 기존 SDK 를 못 버려서 통합이 막히는 첫 사례. 그 전에는 단일 파일
클라이언트 + 목 서버가 통합 마찰을 이미 낮춘다(D7 계약 자기 서빙).

### G7. 스트리밍(SSE) — **보류**

기각이 아니다. "배치 분석 워크로드가 요구하지 않았다" 는 근거는 유효하나, 대화형 소비자가
실재하는 순간 도입 장벽 1순위가 된다.

**해제 조건**: interactive 레인을 쓰는 테넌트의 요구.
**선행 조건**: G1(출력 가드)과의 상호작용 설계 — 청크 단위 검사 창과 위반 시 스트림 중단.
출력 가드 없이 스트리밍을 켜면 **가드를 지나지 않은 텍스트가 실시간으로 나간다.**
순서가 뒤집히면 안 되는 이유가 이것이다.

### G8. 세션(멀티턴) — **보류**

저장·보존·가드·과금 전부에 파급된다. 도입한다면 "세션 누적 위험 스코어" 를 함께 설계한다 —
단발 요청은 무해한데 누적이 위험한 패턴이 업계 공통 미탐 공백이다.
**해제 조건**: 대화형 소비자 + G8 없이는 성립하지 않는 워크로드.

### G9. 캐싱 — **보류**

이 제품은 내부 무료 경로가 주력이라 비용 효익이 작고, 캐시는 **테넌트 간 응답 누출**이라는
새 격리 면을 만든다. 시맨틱 캐시가 테넌트 경계를 넘으면 그 자체가 유출이다 —
격리가 제품의 최대 리스크인데 절감을 위해 새 누출 면을 만드는 거래는 남는 장사가 아니다.
**해제 조건**: 클라우드 티어 비중이 커질 때, **테넌트 내 정확-일치 캐시부터.**

### G10. OTel 내보내기 — **보류**

관측 최소선(잡 단위 토큰·비용·귀속)은 이미 있다. 스팬·트레이스를 자체 구현하는 것보다
**OTel export 한 층**이 실용적이다 — Prometheus `/metrics` 와 같은 급의 외부 연동.
**해제 조건**: 설치처의 기존 관측 스택에 물려야 하는 첫 사례. L2(선언적 체인)를 하게 되면
단계가 곧 스팬이므로 그때 함께 낸다.

### G11. 자동 발견 · 자동 경계 밖 폴백 · 완료 웹훅 — **기각(유지)**

상용 다수가 제공하지만 기존 기각 근거가 여전히 우세하다: 노드가 조용히 늘면 **비용과 데이터
경계가 조용히 는다** / 자동 경계 밖 폴백은 내부가 자는 밤에 민감한 프롬프트를 내보낸다 /
완료 웹훅은 아웃바운드라 인증·SSRF 면을 만든다.

셋 다 "편의를 위해 통제를 자동으로 푸는" 형태이고, **통제가 이 제품의 존재 이유다.**
단, 완료 통지의 **내부** 공백은 별개다 → D13.

### G12. 프롬프트 템플릿 중앙 관리 — **기각**

"프롬프트는 호출자 소유다" 는 두 줄 계약 중 하나다. 서버가 템플릿을 소유하면 소비자는
무엇이 실행됐는지 모르게 되고, 해시 드리프트 감지(C8)의 의미도 사라진다.
서버는 **감지**만 한다 — 조직 표준 지시문은 역할 `system` 기본값이 담당한다.

## 3. 오케스트레이션 (§4 L1–L3)

어떤 층이든 깨면 안 되는 불변식 다섯을 감사서가 정리했고, 그것을 그대로 채택한다:
모든 홉이 가드를 지난다 / 체인의 허용 경계는 단계별 경계의 **교집합** / 비용은 체인 상한으로
선예약 / 판정·라우팅용 LLM 호출은 마스킹본으로 내부 노드에서 / 소비자 계약은 불변.

다섯 번째가 나머지를 지탱한다 — **역할 이름이 계약, 실행 계획도 정책**이다.
오케스트레이션이 API 의 새 표면이 되는 순간 소비자가 계획을 소유하고, 그러면 통제가
소비자 쪽으로 넘어간다.

### L1. 스마트 라우팅 — **채택 · 다음 라운드 이후**

같은 역할 안에서 프롬프트 성격에 따라 싼 모델/비싼 모델을 고르는 층.

**얹기 쉬운 이유가 구조적이다**: "모델은 정책" 과 정합이고(소비자 계약 불변),
판정 인프라가 이미 있으며(가드 2단 분류기 = 마스킹본을 내부 노드 LLM 에 보여주고 판정을
받는 경로 — 라우팅 분류는 그 인프라의 두 번째 소비자다), 실패 모드가 안전하다
(분류 실패 → 정책의 기본 모델. 가드처럼 별도 `on_classifier_error` 가 필요 없다).

**선행 조건**: 감사서가 H1·H2 를 들었고 **둘 다 해소됐다.** 다만 D9(분류기 내성)를
먼저 하는 편이 낫다 — 같은 분류 인프라를 재사용하므로 그 인프라의 결함이 라우팅으로
번지고, 라우팅은 가드와 달리 **오분류가 조용히 비싼 경로를 탄다.**

### L2. 선언적 체인 — **조건부 채택**

역할 하나가 다단계 계획(분해 → fan-out → 통합)을 선언하는 층. 이 제품의 실사용
워크로드가 정확히 map-reduce 형태라 수요 개연성이 있다. 구조 충돌은 없으나 확장 범위가
크다 — 잡 모델(`parent_job_id`), 단계 간 가드 재검사, 체인 상한 선예약, 실패 의미론이
전부 새로 필요하다. DAG 가 아니라 **선형 체인 + fan-out** 으로 제한해야 스케줄러가
단순하게 남는다.

**선행 조건**: D13(완료 이벤트 — 단계 전이가 폴링이면 체인 지연이 단계 수만큼 곱해진다) ·
D6(부모/자식 잡 상태 전이의 원자성) · G1(중간 산출물 검사). 셋이 없으면 체인은 기존 결함을
증폭한다. **해제 조건**: 수요 확인.

### L3-a. 서버측 프롬프트 재작성·증강 — **기각**

"프롬프트는 호출자 소유다" 계약 위반. 서버가 프롬프트를 고치면 소비자는 무엇이 실행됐는지
모르고, 해시 드리프트 감지도 무의미해진다. 조직 표준 지시문은 역할 `system` 기본값이
담당한다 — 그것이 실제로 전달되지 않던 결함(M1)은 이미 고쳤다.

### L3-b. 동적 에이전트 실행 — **보류**

계획이 실행 시점에 생기면 경계·비용의 **사전** 예약이 원리적으로 불가능하다. 에이전트 루프는
소비자 앱의 몫이고, 이 제품은 그 루프의 **각 호출**을 통제하는 게이트웨이로 남는 것이 옳다.
**해제 조건**: 없음(원리적 충돌). 다만 "에이전트 트래픽의 게이트웨이" 포지션 —
세션 귀속(G8) + 툴콜 감사 — 은 로드맵에 남긴다. 그것은 계획을 세우지 않고 **통제만** 한다.

## 4. 다음 라운드 순서

이번 라운드는 문서 정합화였다. 구현 순서는 아래로 확정한다.

| 순서 | 항목 | 상태 |
|---|---|---|
| 1 | **G1 출력 축 (1단)** | ✅ 완료 — 마스킹·봉인·보존·열람 감사 |
| 2 | **D9/G4 분류기 내성** | ✅ 완료 — 울타리·카나리아·탐지 팩 |
| 3 | **G2 시크릿 탐지 팩** | ✅ 완료 — 접두사·문맥. 엔트로피는 실측 후 기각 |
| 4 | **D13 완료 이벤트 + D6 경합 테스트** | ✅ 완료 — 폴링은 진실의 원천으로 남겼다 |
| 5 | D7/G3 멱등성 · D8 TPM 계측 | ✅ 완료 — TPM 은 계기까지, 상한은 실측 후 |
| 6 | **부하 측정** | ✅ 완료 — 아래 P1. 결함 셋을 잡았고 추정 하나를 기각했다 |
| 7 | **D6-b 슬롯 장부 DB 이관** | ✅ 완료 — 지원 구성의 정합성 구멍을 닫았다 |
| 8 | **D4/G5 KEK 회전** | ✅ 완료 — 런북 + `rotate-kek` + 감사. DEK 회전은 기각 |
| 9 | D10 감사 해시 체인 | 해제 조건 도달 시 |
| 10 | 출력 2단(LLM) · 인젝션 전용 분류기 · §4 L1 라우팅 | 지연·비용 실측 후 |

10번의 게이트는 6번으로 **안 열렸다.** 부하 측정은 목 프로바이더로 돌아 컨트롤 플레인만
쟀고, 출력 2단의 대가는 "응답마다 추론이 한 번 더" 라는 **클러스터** 비용이다. 실제
모델이 붙은 환경에서 재기 전까지 이 게이트는 닫혀 있다.

### P1. 가드 1단 스레드 풀 오프로드 — **기각(장치는 유지)**

부하 측정에서 나온 판정이라 감사서 항목이 아니지만, 판정이므로 여기 적는다.
`capacity.md` §6.2-b 는 오래 "임계 초과 프롬프트를 스레드 풀로 넘겨 머리 막힘을
막는다" 고 적어 왔다. **실측으로 틀렸다.**

200KB 제출 2건이 도는 동안 루프 최대 정지는 오프로드를 켰을 때 95.8ms, 껐을 때
95.3ms 였다(각 12회 중앙값). 오프로드가 실제로 걸리는지는 호출을 세어 확인했고,
스캔 자체는 경합 때문에 9% 느려진다. 원인은 `re` 가 **GIL 을 놓지 않는다**는 것이다.

**장치는 남긴다.** 최악값이 경합이 유리하게 풀리면 절반까지 떨어지는 여지가 있고,
끄면 그마저 없다. 다만 **머리 막힘 방어로 세지 않는다** — 그 방어는 역할별
`max_prompt_chars` 다. 기본값 200,000자는 한글이면 475KB 이고 1단만 110ms 다.

이 판정을 여기 적는 이유는 이 문서가 존재하는 이유 그대로다: `capacity.md` 와 부채
표에만 적어 두면 다음 사람이 "오프로드를 켜면 되지 않나" 를 처음부터 다시 저울질한다.

2번이 1번 바로 뒤였던 이유: 분류기가 판정을 하는 이상 그 입력이 곧 공격면이다. 출력 축이
열리면서 가드가 다루는 텍스트의 종류가 늘었으므로 미루면 공격면만 커진다.

출력 2단이 마지막인 이유: 응답마다 추론이 한 번 더 늘어난다. 지연·비용을 실측하기
전에는 켤지 말지를 정할 근거가 없고, 근거 없이 켠 것은 나중에 끄기가 더 어렵다.
