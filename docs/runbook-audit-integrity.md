# 런북 — 감사 무결성

## 이 장치가 주는 것과 주지 않는 것

**먼저 이것부터 읽으세요.** 여기를 건너뛰면 없는 보증을 있다고 말하게 됩니다.

| | |
|---|---|
| ✅ **조작하면 드러난다** | 감사 행마다 앞 행의 해시가 들어갑니다. 한 줄을 고치거나 지우면 그 뒤가 전부 어긋나고 `doctor` 가 그 자리를 지목합니다 |
| ❌ **조작할 수 없다** | 아닙니다. DB 에 쓸 수 있는 사람은 고친 행부터 끝까지 **다시 계산**해 검증을 통과시킬 수 있습니다 |
| ✅ **재계산도 드러난다 — 단, 내보낸 사본이 있을 때만** | 밖으로 내보낸 시점의 팁 해시가 지금 체인에 없으면 재계산된 것입니다 |

> **체인만 두고 "감사 로그가 위변조 불가" 라고 쓰지 마세요.** 사실이 아니고,
> 감사받는 자리에서 그 문장 하나가 나머지 전부의 신뢰를 깎습니다.

진짜 무결성은 **DB 밖**에서 나옵니다. `audit-export` 로 내보낸 파일을 이 호스트가
아닌 곳(SIEM·append-only 버킷·다른 계정의 스토리지)에 두는 것이 그 절반입니다.
같은 호스트에 두면 DB 를 고칠 수 있는 사람이 그 파일도 고칠 수 있어서 대조가
의미를 잃습니다.

## 정기 운영

```sh
lcc audit-export --out /mnt/siem/lcc-audit.jsonl   # 증분. 크론으로
lcc doctor                                          # 체인 + 내보낸 팁 대조
```

`audit-export` 는 증분입니다 — 마지막으로 내보낸 지점 이후만 이어 붙입니다.
1년치를 매번 내보내야 하면 아무도 안 돌리고, **안 돌리는 절차는 없는 절차입니다.**

`doctor` 는 두 가지를 봅니다:

- 체인이 이어지는가 (내부 검증)
- 마지막으로 내보낸 팁이 아직 체인 안에 있는가 (**재계산 탐지**)

## `doctor` 가 문제를 말할 때

### "감사 체인이 어긋납니다"

```
! 감사 체인이 어긋납니다 — 행 내용이 해시와 다릅니다
    id=482 · admin@corp · purge_tenant
```

누군가 그 행을 고쳤거나 지웠습니다. **그 지점이 조작의 시작점입니다** — 그 뒤는
전부 어긋나므로 건수는 의미가 없고, 봐야 할 것은 `id` 와 그 시각입니다.

1. **DB 를 더 건드리지 마세요.** 재계산으로 "고치면" 증거가 사라집니다.
2. 내보낸 사본에서 그 `id` 주변을 찾으세요. 사본에 원본이 있습니다.
3. 사본과 DB 를 대조해 무엇이 바뀌었는지 특정하세요.
4. 그 시점에 DB 파일에 접근할 수 있었던 경로를 조사하세요 — 호스트 접근, 백업
   복원, 다른 도구의 직접 쓰기.

사본이 없다면 **무엇이 바뀌었는지 알 방법이 없습니다.** 그것이 내보내기를 정기
실행하라는 이유입니다.

### "마지막으로 내보낸 감사 팁이 지금 체인에 없습니다"

```
! 마지막으로 내보낸 감사 팁이 지금 체인에 없습니다 — 체인이 재계산됐을 수 있습니다.
```

**체인 검증만으로는 절대 못 잡는 사건입니다.** 체인은 통과하는데(다시 계산했으니)
밖에 있는 사본만이 원래 무엇이었는지 압니다.

1. 내보낸 파일의 마지막 줄에서 `row_hash` 를 확인하세요.
2. 그 해시가 DB 에 없다면 그 지점 이후가 다시 쓰였습니다.
3. 사본의 행들과 DB 의 같은 `id` 를 대조하세요.

**정상인데 이 경고가 뜨는 경우 하나**: 보존 기간(365일)이 지나 내보낸 팁의 행이
정리됐을 때입니다. 내보낸 파일의 마지막 `ts` 가 1년보다 오래됐다면 그쪽입니다 —
그 경우 `audit-export` 를 한 번 돌리면 기준점이 최신으로 갱신됩니다.

## 정상인데 사고처럼 보이는 것들

이 셋은 **정상 동작**이고, 그래서 검증이 신고하지 않도록 설계돼 있습니다. 신고한다면
그것이 버그입니다.

| 동작 | 왜 체인을 건드리나 | 어떻게 다루나 |
|---|---|---|
| **보존 정리** (365일) | 옛 행을 지우므로 살아남은 첫 행의 앞 고리가 사라진다 | 지우기 직전 마지막 행의 해시를 앵커로 남기고, 검증은 거기서부터 잇는다 |
| **합치기** (대시보드 폴링) | 행을 고치는 연산이다 | **체인의 끝일 때만** 합친다. 그 사이 다른 사건이 기록됐으면 새 행을 쓴다 |
| **업그레이드 이전 행** | 해시 컬럼이 NULL | "검증 대상 아님" 으로 센다. 소급 계산하지 않는다 — 소급 계산은 "그때 이 값이었다" 를 증명하지 못하면서 증명한 것처럼 보이게 만든다 |

**정상 운영을 사고로 신고하는 검증은 곧 꺼집니다.** 그래서 이 셋이 설계에 들어가
있고, `tests/test_audit_chain.py` 가 각각을 고정합니다.

## 다중 워커에서

API 워커를 여러 개 띄우면 두 워커가 같은 체인 끝을 나란히 읽는 창이 열립니다.
그대로 두면 같은 앞 고리를 가진 행이 둘 생기고(**포크**), 검증은 그것을 조작과
구분하지 못합니다.

`admin_audit(prev_hash)` 에 유일 인덱스가 걸려 있어 DB 가 포크를 막습니다. 진 워커는
삽입에 실패하고 새 끝을 읽어 다시 잇습니다 — **감사 기록을 잃지 않는 것이 우선**이라
포기하지 않고 재시도합니다. `tests/test_multiprocess.py` 가 진짜 프로세스로 잽니다.

같은 수법을 잡의 멱등성 키와 노드 슬롯도 씁니다(architecture.md §11).

## 내보낸 파일의 형식

JSONL 입니다. 한 줄이 한 행이고, 해시가 함께 들어 있어 **밖에서 독립적으로 검증**할
수 있습니다.

```json
{"id": 482, "ts": 1767225600.0, "tenant_id": "acme", "actor": "admin@corp",
 "action": "purge_tenant", "target": "acme", "detail_json": "{}", "outcome": "ok",
 "prev_hash": "9f2c…", "row_hash": "d668…"}
```

해시 계산은 `app/store.py` 의 `audit_row_hash` 입니다:

```
sha256(prev_hash ␟ ts ␟ tenant_id ␟ actor ␟ action ␟ target ␟ detail_json ␟ outcome)
```

`␟` 는 0x1F(unit separator)입니다. 구분자가 데이터에 나타날 수 있으면 필드 경계를
옮기면서 같은 해시를 유지할 수 있는데, `json.dumps` 가 제어문자를 `\uXXXX` 로
이스케이프하므로 0x1F 는 어느 필드에도 안 나옵니다.

`ts` 는 소수점 6자리로 포맷합니다(`f"{ts:.6f}"`).
