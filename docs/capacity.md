# 규모 산정

설치처가 자기 물량을 대입해 서버 규모를 정하는 문서. 임계값은 전부
[`config/thresholds.yaml`](../config/thresholds.yaml) 한 곳에서 읽고 이 문서는 그 파일을 인용한다 —
문서의 숫자와 코드의 임계값이 갈라지면 "손으로 관리하는 표는 반드시 어긋난다" 를 그대로 반복한다.

---

## 1. 레퍼런스 워크로드 프로파일

산정의 기준선은 실제로 돌던 시스템의 실측값이다.
출처: 이전 게이트웨이의 `usage` 테이블(30일 보존), 조회 시점 2026-08.

| 지표 | 값 |
|---|---|
| 호출 | 106,368 건 / 30일 = **3,546 건/일** |
| 평균 지연 | **3,284 ms/호출** |
| 평균 출력 토큰 | 210 토큰/호출 |
| 누적 GPU 점유 | 97.0 시간 → **가동률 13.5%** (직렬 슬롯 1개 기준) |
| 성공률 | 89.2% (실패 10.8% 도 GPU 를 먹는다) |

이 프로파일은 **뉴스·공시 분류 워크로드**(짧은 출력, 중간 입력, 버스트성)의 특성이다.
워크로드가 다르면 아래 공식에 자기 값을 넣는다.

---

## 2. 산정 공식

```
필요 슬롯 = (피크 호출률 [건/분] × 평균 지연 [초]) ÷ (60 × 목표 점유율)

목표 점유율 0.7 권장 — 버스트·재시도 여유
```

레퍼런스 프로파일 대입(일 물량의 70% 가 10시간에, 버스트는 그 평균의 3~5배):

```
활성 평균 = 3,546 × 0.7 ÷ 10 ÷ 60 = 4.1 건/분
버스트    = 12~20 건/분
필요 슬롯 = 15 × 3.28 ÷ (60 × 0.7) = 1.17 → 2 슬롯
```

> **평균만 보면 1대로 충분(13.5%)하지만 버스트가 단일 슬롯의 80% 를 먹는다.**
> 여기에 실패율 10.8% 의 재시도가 겹치면 큐가 쌓인다 — 레인 동시성 > 1 이 필요하고,
> 그게 메모리 헤드룸을 요구한다. **노드를 늘리는 근거는 처리량이 아니라 가용성과 피크다.**

## 3. 가드 2단이 추가하는 부하

| 추가분 | 산정 | 영향 |
|---|---|---|
| **가드 2단 LLM 분류** | 필터 대상 요청당 +1회, 소형 모델 ~0.5초 | 호출 수 **최대 2배**, GPU 시간 **+15%** |
| 1단 패턴 · 해싱 · 암호화 · 헬스 폴링 | µs~ms 단위 | 무시 가능 |

호출 수는 2배지만 GPU 시간은 +15% 뿐이다 — 분류 모델이 훨씬 작기 때문.
프롬프트 해시 캐시가 먹히면 더 낮다.

> **가드는 전용 레인을 쓴다.** 분류 잡이 대형 batch 잡 뒤에 줄 서면 필터 한 번에 수 분이 걸린다.
> 보안 경로가 head-of-line blocking 에 걸리는 것은 설계 실패다.

## 4. 서버 대수 — LLM 노드 제외

**컨트롤 플레인은 1대다** (Demo·Starter·Standard). 그 1대에 컨테이너 3개가 돈다.

별도 서버가 생기지 않는 이유:

| 흔히 필요한 것 | 이 설계 | 근거 |
|---|---|---|
| 노드 에이전트 서버 | 없음 | 엔드포인트 등록형 — 노드에 아무것도 설치 안 함 |
| 별도 웹서버 | 없음 | 관제 UI 를 컨트롤 플레인이 직접 서빙 |
| 메시지 브로커 | 없음 | 잡 큐가 DB 테이블 |
| 캐시 서버 | 없음 | 헬스·모델 인벤토리는 프로세스 메모리 |
| 워커 서버 | 없음 | 추론은 전부 LLM 노드. 가드 분류도 노드에서 돈다 |

| 프로파일 | 컨트롤 플레인 서버 |
|---|---:|
| Demo | **1대** (노트북. 노드도 목으로 대체하면 총 1대) |
| Starter | **1대** |
| Standard | **1대** |
| Scale | 3~4대 — 앱 ×2 + Postgres ×1(+standby) |

**서버는 아니지만 별도 위치가 필요한 것**: ① 백업 저장소 ② 마스터 KEK.
둘을 컨트롤 플레인 호스트에 함께 두면 1대 구성의 단순함이 그대로 단일 실패점이 되고,
백업이 유출되면 암호문도 함께 열린다.

## 5. 프로파일별 권장 사양

| | Demo | Starter | Standard | Scale |
|---|---|---|---|---|
| 컨트롤 플레인 vCPU / RAM | **1 / 512 MB** | 2 / 4 GB | 4 / 8 GB | 4×N / 8 GB |
| DB | SQLite | SQLite | SQLite 또는 PG | Postgres |
| 디스크 | **2 GB** | 50 GB | 100~200 GB | 별도 볼륨 |
| LLM 노드 | 목 (+선택 소형 1) | 내장 1 (16~24 GB) | 2~3 (24~48 GB) | 4+, 모델 2중 호밍 |
| 레인 동시성 | int 1 / batch 1 / guard 1 | int 2 / batch 1 / guard 2 | int 3 / batch 2 / guard 4 | 설정값 |

**컨트롤 플레인 절대 최소치는 1 코어 / 512 MB / 2 GB 디스크다.** 추론을 하지 않으므로
파이썬 런타임 ~80 MB + 대형 프롬프트 처리 시 건당 2~3 MB 가 전부다.

**노드 메모리 산정**: 동시에 상주할 모델 크기의 합 + 20% 여유.
예) 대형 20GB + 중형 9GB + 가드 1.2GB = 30.2GB → 예산 40GB 노드 1대 또는 분산 2대.

## 6. 사용자가 늘면 감당하는가

**결론: 컨트롤 플레인은 병목이 아니다.** 클러스터가 훨씬 먼저 막힌다.

### 6.1 요청당 CPU — 실측 (제출 경로)

`python -m app.loadtest` 로 잰 값이다. 목 프로바이더로 돌므로 **컨트롤 플레인의
한계**이지 클러스터 처리량이 아니다.

측정 환경: Linux x86_64 · Python 3.11.15 · **4코어** · SQLite(WAL, 디스크).

| 단계 | 추정이었던 값 | **실측** | 판정 |
|---|---:|---:|---|
| 인증 (해시 조회 + HMAC) | 0.05 ms | **0.002 ms** | 추정이 25배 비관적 |
| **가드 1단 정규식** (4KB) | 1.5 ms | **0.889 ms** | 추정이 보수적 |
| AES-256-GCM 4KB | 0.003 ms | **0.007 ms** | 자릿수 일치 |
| DB 조회 1건 | 0.3 ms | **0.003 ms** | 추정이 100배 비관적 |
| **제출 종단 4KB** (ASGI 통과) | ≈ 2 ms → 250/초 | **2.2 ms → 454/초** | **추정이 옳았다** |
| 제출 종단 40KB | 15 ms → 60/초 | **11.7 ms → 86/초** | 추정이 보수적 |
| 제출 종단 200KB | 40~80 ms → 12~25/초 | **48.7 ms → 21/초** | 구간 안 |
| **조회(폴링)** | **2,000/초** | **311/초** | **6.4배 빗나갔다** ↓ |

**폴링 추정이 유일하게 크게 틀렸다.** 그리고 그 원인은 성능 퇴행이 아니라 §6.2-a 의
방어 장치들이다 — 추정 이후에 폴링 전용 레이트리밋(쓰기 1회)·큐 위치 계산·적응형
`retry_after` 가 붙었고, 그것들이 조회 한 건을 0.003ms 에서 3.2ms 로 만들었다.
파국 경로를 막는 대가로 낸 값이므로 **되돌릴 대상이 아니라 기록할 대상**이다.
그래도 결론은 안 바뀐다: 노드 3대 × 슬롯 3개 클러스터의 상한 2.7 job/초 대비
여전히 100배 이상 여유다.

> **부하 테스트로 검증했다.** 설치처의 하드웨어는 다르다 — 같은 도구를 자기
> 장비에서 돌려 자기 값을 쓰라. 그러라고 번들에 들어 있다.

### 6.2 클러스터와 무관하게 늘어나는 것

**(a) 폴링 — 유일하게 파국으로 가는 경로**

```
클러스터 포화 → 큐 증가 → 대기 잡 증가 → 폴링 증가 → 컨트롤 플레인 과부하
                  ↑                                        │
                  └────────────── 응답 지연 ←──────────────┘
```

대기 잡 10,000건이 2초마다 폴링하면 5,000 req/초로 1코어 한계를 넘는다.
**컨트롤 플레인이 자기 부하가 아니라 클러스터 포화의 *증상*으로 죽는다.**
→ 상태 조회에 별도 레이트리밋 + 큐 위치 기반 **적응형 `retry_after`** + `wait` 사용 권고.

**큐 깊이별 폴 원가 — 실측.** 이 피드백 루프에서 가장 위험한 성질은 "큐가 깊어질수록
폴이 비싸지는 것" 이다. 그러면 방어 장치가 오히려 루프를 증폭한다.

| 큐 깊이 | 폴 1건 |
|---:|---:|
| 291 건 | 3.13 ms |
| 500 건 | 3.49 ms |
| 1,000 건 | 4.35 ms |

깊이가 3.4배 늘 때 원가는 1.4배다 — 준선형이라 루프를 증폭하지 않는다.

> **처음 재었을 때는 그렇지 않았다.** 큐 위치 계산이 후보 행을 최대 500건까지
> 통째로 읽어 와서, 깊이 0 에서 0.72ms 이던 폴이 깊이 1,000 에서 28.0ms 로
> **39배** 뛰었다. 적응형 `retry_after` 가 damp 하려던 바로 그 루프를 그 계산이
> 증폭하고 있었다. `SELECT COUNT(*)` 로 바꿔 위 표가 됐다.
> 부하 테스트가 없었으면 못 봤을 결함이다.

**(b) 큰 프롬프트 × 가드 정규식**

| 프롬프트 | 가드 1단 (실측) | 제출 종단 (실측) |
|---|---:|---:|
| 4 KB | 0.89 ms | 2.2 ms → 454/초 |
| 40 KB | 8.81 ms | 11.7 ms → 86/초 |
| 200 KB | 42.4 ms | 48.7 ms → 21/초 |
| **475 KB** = `max_prompt_chars` 200,000자 | **110 ms** | — |

동기로 이벤트 루프 위에서 돌면 그동안 다른 모든 요청이 멈춘다.

> **정규화가 규칙마다 돌고 있었다.** 텍스트 정규화(NFKC·zero-width 제거)는 텍스트의
> 성질인데 규칙 루프 안에 있어서, 규칙 30개짜리 프롬프트는 같은 문자열을 30번
> 정규화했다. 200KB 한 건에서 25ms 가 그렇게 샜다. 스캔 바깥으로 끌어올려
> 종단 200KB 가 **75ms → 49ms**, 40KB 가 **17ms → 12ms** 가 됐다.
> 이 표의 실측값은 그 수정 **이후**의 값이다.

**스레드 풀 오프로드는 머리 막힘을 막지 못한다 — 실측으로 기각한다.**

`stage1_threadpool_threshold_bytes`(기본 16KB) 초과 프롬프트의 1단은 스레드 풀로
넘어간다. 이 문서는 그것이 머리 막힘을 막는다고 적어 왔다. **아니다.**

200KB 제출 2건이 도는 동안 2ms마다 깨어나기만 하는 감시견으로 루프 정지를 재고,
임계만 올려 오프로드를 끈 대조군과 나란히 놓았다(각 12회, 중앙값):

| 구성 | 루프 정지 (중앙) | 범위 |
|---|---:|---:|
| 오프로드 켬 | 95.8 ms | 89.6 ~ 108.9 |
| 오프로드 끔 | 95.3 ms | 89.9 ~ 102.2 |

**차이가 없다.** 오프로드가 실제로 걸렸는지는 호출을 세어 확인했고(2/2), 스캔 자체는
경합 때문에 오히려 9% 느려진다. 원인은 `re` 가 **GIL 을 놓지 않는다**는 것이다 —
스캔을 다른 스레드로 옮겨도 그 스레드가 GIL 을 쥐고 있으므로, 자기 일을 하려면
GIL 이 필요한 이벤트 루프는 여전히 선다.

가드만 떼어 재면 오프로드가 정지를 3분의 1로 줄인다(116ms → 21ms). 그 측정에서는
루프에 감시견 말고 할 일이 없어서 GIL 을 조르는 쪽이 이긴다. **부하가 실린 실제
요청 경로에서는 그 이점이 사라진다** — 재는 자리를 잘못 고르면 정반대 결론이 난다.

→ 큰 프롬프트에 대한 실효 방어는 스레드 풀이 아니라 **`max_prompt_chars`** 다.
기본값 200,000자는 한글이면 475KB 이고 1단만 **110ms** 다. 대화형 레인에서 그
정지가 문제라면 역할별로 `max_prompt_chars` 를 낮추는 것이 유일하게 듣는 손잡이다.
오프로드는 유지하되(끄면 최악값이 조금 나빠진다) **머리 막힘 방어로 세지 말 것.**

**(c) 스토리지·집계** — 사용량 테이블이 1,000만 행을 넘으면 롤업 테이블 도입 시점이다.

### 6.3 엔드유저 30,000명 시나리오

테넌트 100 × 서비스 3 × 엔드유저 100, 1인당 10건/일 = **30만 건/일**:

| 항목 | 필요량 | 판정 |
|---|---|---|
| 컨트롤 플레인 | 평균 3.5/초, 피크 20/초 | **1대로 충분** |
| **LLM 노드** | 20/초 × 3.3초 = 동시 66슬롯 | **약 22대** ← 비용의 실체 |
| 스토리지 | 3 GB/일 = 90 GB/월 | **Postgres 전환** |
| 폴링 | 대기 잡에 비례 | `wait` 권고 + 적응형 백오프로 방어 |

## 7. 스토리지 산정

행당 ~10 KB (마스킹본 4 + 암호문 4 + 응답 1 + 메타·인덱스 1) 기준:

```
일 증가        = 호출/일 × 10 KB          (레퍼런스: 35 MB/일)
잡 보존 30일    = 일 증가 × 30             (1.05 GB)
암호문 7일      = 호출/일 × 4 KB × 7       (100 MB)
usage·감사·필터 = 잡의 30%                 (0.3 GB)
WAL·인덱스 여유 = 소계 × 2
────────────────────────────────────────
레퍼런스 정상 상태 ≈ 1.5 GB → 10배 성장 여유 포함 30 GB
```

→ Demo 2 GB, Starter 50 GB, Standard 100~200 GB.
**SQLite 는 이 규모에서 병목이 아니다** (전환 트리거는 아래).

## 8. 증설·전환 트리거

관제 UI 가 아래를 넘으면 경고한다. 값은 `config/thresholds.yaml` 이 권위다.

| 지표 | 설정 키 | 기본 임계 | 조치 |
|---|---|---|---|
| 레인 슬롯 점유율 (5분 평균) | `lane_utilization_warn` | 0.70 | 노드 증설 |
| 큐 대기 p95 | `queue_wait_p95_seconds` | 30초 | 레인 동시성 상향 → 노드 증설 |
| 기아 방지 발동 | `starvation_trips_per_day` | 10회/일 | 배치 경합 — 노드 증설 |
| 노드 메모리 예산 거부율 | `node_memory_reject_rate` | 0.05 | 해당 노드 메모리 증설 |
| 단일 호밍 역할의 노드 점유율 | `single_homed_node_utilization` | 0.60 | 모델을 2번째 노드에 복제 |
| 클라우드 비용 소진율 | `cost_budget_burn_warn` | 0.80 | 배치 정책 점검 |
| **DB 크기** | `db_size_gb_migrate` | **50 GB** | **SQLite → Postgres 전환** |
| **테넌트 수** | `tenant_count_scale_profile` | **20** | **Scale 프로파일 검토** |
| 스캔 창 절단 | `scan_window_per_lane` | 50 | 상한 상향 또는 노드 증설 |
