# 플러그인 시스템 기술 탐색

**상태: 탐색 결과. 아직 결정이 아니다.** 판정은 [design-decisions.md](design-decisions.md) 에서 내리고,
구현된 기능은 [feature-spec.md](feature-spec.md) 가 적는다. 이 문서는 그 앞 단계다.

요구: 플러그인을 **패키지 형태로 개발**해서 **설치**하고, **관리자 대시보드에서 관리**하며
**active/inactive** 를 토글한다.

---

## 0. 먼저 말할 것 — 탐색에서 나온 결정적 사실

이 제품에서 플러그인은 일반적인 확장 기능이 아니라 **보안 경계 문제**다. 이유는 하나다.

> 이 제품이 지키는 불변식은 전부 **`app/` 을 정적 분석해서** 강제된다.
> `tests/test_architecture.py` 의 `SOURCES = sorted(APP.rglob("*.py"))` 가 그 범위다.

그 검사가 지키는 것은 이렇다.

| 검사 | 막는 것 |
|---|---|
| `test_only_the_store_touches_the_connection` | `_scoped_where()` 를 지나지 않는 DB 질의 |
| `test_only_the_pipeline_creates_jobs` | 가드를 건너뛴 잡 생성 |
| `test_only_the_scheduler_writes_the_response` | 출력 검사를 지나지 않은 응답 쓰기 |
| `test_filter_events_cannot_record_the_matched_value` | 탐지 로그에 원문 값이 남는 것 |
| `test_partial_masking_cannot_keep_the_whole_value` | 부분 마스킹이 전체를 남기는 것 |

**플러그인은 정의상 `app/` 밖에 있다.** 인프로세스로 로드하는 순간 위 다섯 개가 그 코드에는
적용되지 않는다. 악의가 있어서가 아니라 **검사기가 거기까지 안 간다**. 플러그인 하나가
`store._conn` 을 잡으면 테넌트 격리는 그 시점부터 없는 것이다.

이 제품의 문서는 "구조 > 규율" 을 계속 말해 왔다(architecture §13-8). 플러그인 저자에게
"프롬프트를 읽지 마세요" 라고 **부탁하는** 설계는 이 제품이 3회의 감사를 거치며 배운 것을
정면으로 뒤집는다. 그래서 이 탐색의 축은 "어떤 훅을 열까" 가 아니라 **"플러그인 코드가 어디서
도는가"** 다.

## 1. 이 제품이 플러그인에 거는 제약

일반적인 플러그인 시스템 설계와 다르게 잡아야 하는 조건들이다.

| 제약 | 어디서 오나 | 플러그인에 미치는 영향 |
|---|---|---|
| **외부 패키지 5개** | 이식성·보안 검토 표면 (`pyproject.toml`) | 플러그인 프레임워크에 새 의존성을 못 쓴다 |
| **에어갭 설치** | CLUSTER-9 · PKG-4 | PyPI 에서 받는 설치는 애초에 안 된다. 파일이어야 한다 |
| **원문 비유출** | GUARD-5 · CRYPTO-1 | 프롬프트를 보는 플러그인은 새 유출 경로다 |
| **테넌트 격리** | DATA-1 | 플러그인이 스코프를 우회하면 격리가 끝난다 |
| **감사 해시 사슬** | CRYPTO-4 | 설치·활성·비활성이 전부 사슬에 들어가야 한다 |
| **DB 가 권위** | architecture §10 | 플러그인 상태는 파일이 아니라 DB 에 있어야 한다 |
| **장애 반경 격리** | `test_blast_radius.py` | 플러그인 하나가 컨트롤 플레인을 죽이면 안 된다 |
| **doctor 가 진단한다** | OPS-5 | 깨진 플러그인을 사람 말로 짚어야 한다 |
| **손으로 관리하는 표는 어긋난다** | architecture §13-8 | 플러그인 목록에도 드리프트 장치가 필요하다 |

## 2. 이미 있는 확장 지점 두 개

플러그인을 처음부터 설계할 필요가 없다. **이 저장소에는 이미 두 가지 확장 패턴이 있고,
그 둘은 서로 다른 실행 모델을 쓴다.** 이것이 등급을 나누는 근거가 된다.

### 2-1. 프로바이더 레지스트리 — 인프로세스

```python
# app/providers/base.py
_REGISTRY: dict[str, Callable[..., Provider]] = {}

def register(name: str): ...          # 데코레이터로 임포트 시점에 등록
def build_provider(node): ...         # 노드 선언에서 인스턴스를 만든다
def known_providers() -> tuple[str, ...]: ...
```

`ollama` · `anthropic` · `mock` 세 개가 이 레지스트리에 있다. 이건 **본질적으로 인프로세스여야
한다** — 프로바이더는 HTTP 클라이언트이고, 노드 호출 경로 한가운데 있다.

### 2-2. 알림 채널 — 이미 프로세스 밖

```python
# app/notify.py
class Channel(Protocol):
    blocking: bool                     # 막는지 아닌지를 채널이 선언한다
    def send(self, event, detail) -> None: ...
```

`WebhookChannel` 은 **이미 아웃오브프로세스 플러그인이다.** HTTP 로 나가고, 받는 쪽이 뭘 하든
컨트롤 플레인은 모른다. 그리고 이 패턴은 이미 세 가지를 해결해 뒀다.

- `redact()` 가 나가는 페이로드에서 프롬프트와 비밀을 벗긴다 → **호스트가 무엇을 보낼지 정한다**
- `test_a_dead_channel_never_kills_the_caller` → 실패를 삼킨다
- `blocking` 을 선언 안 하면 **막는다고 가정한다**(`test_a_channel_is_assumed_to_block_unless_it_says_otherwise`) → 안전한 쪽 기본값

플러그인 설계는 이 두 번째 패턴을 일반화하는 것에서 출발해야 한다. 첫 번째(인프로세스)는
**예외로 다루고 비용을 따로 치른다.**

## 3. 핵심 질문 — 플러그인 코드가 어디서 도는가

### 선택지

| 모델 | 격리 | 지연 | 새 의존성 | 이 제품에서의 문제 |
|---|---|---|---|---|
| **A. 인프로세스 파이썬** | 없음 | 0 | 0 | §0 의 다섯 불변식이 전부 무효. 마스터 KEK 도 같은 메모리에 있다 |
| **B. 서브프로세스 + IPC** | OS 프로세스 | ~1–5ms | 0 (stdlib `subprocess`) | 실행 파일을 신뢰해야 하는 건 같다. 다만 메모리는 못 본다 |
| **C. HTTP 아웃오브프로세스** | 네트워크 | ~1–10ms | 0 (`httpx` 이미 있음) | 이미 `notify` 가 이 모델. 플러그인이 별도 서비스여야 한다 |
| **D. WASM 샌드박스** | 강함 | ~0.1ms | **wasmtime 등 신규** | 5개 원칙 위반. 파이썬 플러그인을 못 씀 |
| **E. 코드 없음 (선언형)** | 완전 | 0 | 0 | 표현력이 설정이 표현할 수 있는 데까지 |

### 판단

**D 는 탈락한다** — 새 의존성이 크고(수십 MB), 에어갭 번들이 무거워지며, 플러그인 저자가
파이썬을 못 쓴다. 이 제품의 5개 원칙과 정면 충돌한다.

**A 를 기본값으로 두면 안 된다.** 다만 프로바이더처럼 **본질적으로 인프로세스여야 하는
확장**이 실재하므로 완전히 닫을 수도 없다.

→ **등급을 나눈다.** 대부분의 플러그인은 코드가 필요 없고(E), 코드가 필요한 것 대부분은
바깥에서 돌 수 있으며(C/B), 진짜 인프로세스여야 하는 것만 명시적으로 높은 신뢰를 요구한다(A).

## 4. 제안 — 3등급 플러그인

### 등급 1 · 선언형 (`declarative`)

**코드가 없다.** 번들 안에 데이터 파일만 들어 있고, 호스트가 그것을 읽어 자기 코드로 처리한다.

| 무엇을 확장하나 | 지금 어디에 있나 |
|---|---|
| 가드 규칙 팩 (새 나라 PII, 산업별 패턴) | `config/guard.yaml` `locale_packs` |
| 가드 맥락 규칙 세트 | `config/guard.yaml` `context_rules` |
| 정답셋 픽스처 (GUARD-11) · 라우팅 픽스처 (ROUTE-4) | `store` `eval_fixtures` |
| 모델 카탈로그 항목 | `config/catalog.yaml` |
| 단가표 | `config/pricing.yaml` |
| 로케일 카탈로그 | `locales/` |
| 대시보드 패널 (읽기 전용 · 기존 API 조합) | `static/app.js` `tabsFor` |

**이 등급이 예상 수요의 대부분을 덮는다.** "우리 회사 사번 형식을 PII 로 잡아 줘",
"이 산업 규제 용어를 맥락 규칙으로 넣어 줘", "우리 워크로드 기준 라우팅 픽스처" 는 전부
코드가 아니라 데이터다. 그리고 이 등급은 **§0 의 다섯 불변식을 하나도 건드리지 않는다** —
플러그인이 코드를 실행하지 않기 때문이다.

**위험**: 규칙 팩은 코드는 아니지만 정규식이다. 파국적 백트래킹(ReDoS)이 가능하다.
기존 `Guard.validate_rule` 과 `probe_rule` 이 이미 검증 지점이므로 여기에 시간 상한을 건다.

### 등급 2 · 외부 실행형 (`external`)

**플러그인이 별도 프로세스/서비스이고 호스트는 정해진 페이로드만 보낸다.** `notify` 웹훅의
일반화다.

| 확장 지점 | 호스트가 보내는 것 | 플러그인이 돌려주는 것 |
|---|---|---|
| 알림 채널 | `redact()` 통과한 이벤트 | 없음 (fire-and-forget) |
| 잡 완료 훅 | 잡 ID · 상태 · 사용량 (본문 없음) | 없음 |
| 감사 싱크 (SIEM 연동) | 감사 행 + 해시 | 없음 |
| 사용량 익스포터 | 집계 수치 | 없음 |
| 외부 판정기 (선택적) | **마스킹본** | 구조화 판정 |

**계약이 곧 경계다.** 호스트가 보내는 페이로드에 원문이 없으면 플러그인은 원문을 볼 수 없다.
`notify.redact()` 가 이미 그 일을 하고 있고, `test_a_notification_never_carries_the_prompt` 가
고정하고 있다. 같은 장치를 플러그인 페이로드에 재사용한다.

**위험**: 네트워크로 나간다는 것 자체가 데이터 경계 문제다. 에어갭 모드에서는 외부 주소를 가진
플러그인을 **배치 단계에서 막는 것과 같은 방식으로** 막아야 한다(CLUSTER-9 재사용).

### 등급 3 · 인프로세스 (`native`)

**호스트 프로세스 안에서 파이썬 코드가 돈다.** 프로바이더가 유일하게 정당한 사례다.

이 등급은 **"이 플러그인은 컨트롤 플레인과 같은 권한을 갖는다" 를 설치 시점에 사람이
확인해야** 한다. Elasticsearch 가 플러그인 설치 때 요구 권한을 화면에 찍고 `y` 를 받는 것과
같은 이유다. 숨기면 설치처는 그것이 안전하다고 믿는다.

추가로 붙는 조건:
- **서명 필수** (등급 1·2 는 선택)
- 설치 시 **재시작 필요** (§7 참고)
- `doctor` 가 native 플러그인의 존재를 항상 보고한다 — 감사자가 "이 설치처에는 서드파티 코드가
  돈다" 를 알아야 한다

## 5. 패키지 포맷

### 왜 wheel / `pip install` 이 아닌가

플러그인을 파이썬 휠로 만들고 `pip install` 하는 것이 가장 쉬워 보이지만, 이 제품에서는 넷이 깨진다.

1. **에어갭** — `pip install` 은 기본이 네트워크다. `--no-index --find-links` 로 돌릴 수 있지만
   그건 이미 파일 기반 설치를 흉내 내는 것이다
2. **의존성 5개 원칙** — 플러그인이 자기 의존성을 끌고 들어와 호스트의 그래프를 바꾼다.
   "이 설치본이 무엇을 임포트하는가" 가 더 이상 `pyproject.toml` 로 답이 안 된다
3. **되돌리기** — `pip uninstall` 은 남는 파일과 dist-info 를 남긴다. 비활성화 ≠ 제거인데
   `pip` 에는 비활성 개념이 없다
4. **런타임 설치** — 도는 서버가 자기 venv 를 바꾸는 것은 컨테이너 이미지 불변성과 충돌한다
   (`Dockerfile` · `compose.yml` 전제)

### 제안 — 서명된 zip 번들

```
acme-guard-pack-1.2.0.lccp          ← 그냥 zip 이다. 확장자만 다르다
├── plugin.toml                      매니페스트 (필수)
├── SIGNATURE                        Ed25519 detached 서명 (native 는 필수)
├── payload/
│   ├── rules/kr-employee-id.yaml    등급 1: 데이터
│   ├── fixtures/*.jsonl
│   └── panel.js                     등급 1: 대시보드 패널
└── LICENSE  README.md
```

**서명에 새 의존성이 0 이다.** `cryptography>=42` 가 이미 의존성이고 Ed25519 를 지원한다.
`zipfile` · `hashlib` · `tomllib` 은 전부 stdlib(3.11). 실측으로 확인했다.

### 매니페스트 초안

```toml
[plugin]
id            = "acme.guard.kr-employee-id"   # 역DNS. 전역 유일
name          = "사번 탐지 팩"
version       = "1.2.0"
tier          = "declarative"                  # declarative | external | native
requires_host = ">=0.2,<0.3"                   # 호스트 API 버전 범위
description   = "사내 사번 형식을 PII 로 탐지한다"

[capabilities]                                  # 요구 권한. 설치 화면에 그대로 찍힌다
guard_rules   = true                            # 가드 규칙을 더한다
dashboard     = true                            # 대시보드 패널을 붙인다
reads_prompt  = false                           # 원문을 보는가 — native 만 true 가능
network       = []                              # 나가는 주소. 에어갭에서 검사한다

[entry]                                          # 등급별로 의미가 다르다
rules     = ["payload/rules/kr-employee-id.yaml"]
panel     = "payload/panel.js"
# external: endpoint = "https://..."  ·  native: module = "acme_plugin:setup"
```

**설계 의도**: `[capabilities]` 는 **문서가 아니라 강제 대상**이다. `guard_rules = false` 인
플러그인이 규칙 파일을 담고 있으면 설치가 거부된다. 매니페스트가 하는 말과 번들 내용이
어긋나면 설치 단계에서 잡는다 — 이 저장소의 드리프트 장치와 같은 사고방식이다.

### 매니페스트를 TOML 로 할까 YAML 로 할까

| | TOML (`tomllib`, stdlib) | YAML (`PyYAML`, 이미 의존성) |
|---|---|---|
| 일관성 | `config/` 는 전부 YAML 이라 어긋난다 | 저장소 관행과 같다 |
| 공격 표면 | 읽기 전용 파서. 앵커·별칭·태그가 없다 | `safe_load` 면 안전하지만 앵커 폭탄(billion laughs)은 남는다 |
| 성격 | **신뢰하지 않는 아티팩트**의 매니페스트 | `config/` 는 운영자 소유(신뢰됨) |

→ 신뢰 수준이 다른 입력이므로 **TOML 쪽으로 기운다.** `config/` 가 YAML 인 것은 그것이
운영자가 직접 쓰는 파일이기 때문이고, 플러그인 매니페스트는 남이 준 파일이다.
다만 이건 결정 사항이다(§11).

## 6. 설치 절차

```
① 업로드        POST /v1/platform/plugins        body = 번들 바이트 (플랫폼 관리자)
② 형식 검증      zip 인가 · plugin.toml 이 있는가 · 크기 상한
③ 서명 검증      SIGNATURE ↔ 신뢰 키 목록. native 는 실패 시 즉시 거부
④ 매니페스트 검증  id 형식 · requires_host 범위 · tier 별 필수 필드
⑤ 내용 대조      [capabilities] 가 말한 것과 payload 가 담은 것이 일치하는가
⑥ 권한 표시      요구 권한을 화면에 찍고 관리자 확인을 받는다 (native 는 문구 입력)
⑦ 디스크에 풀기   plugins/<id>/<version>/  ← 경로 순회 방어 필수
⑧ DB 등록        상태 = installed, **inactive**
⑨ 감사           admin_audit 해시 사슬에 기록
──────────────────────────────────────────────
⑩ 활성화 (별도)  POST /v1/platform/plugins/{id}/activate
```

### 설계 근거

**설치와 활성화를 나눈다.** 올려놓는 것과 도는 것은 다른 결정이다. 모델 설치 요청이
승인과 나뉘어 있는 것(CLUSTER-11)과 같은 구조다.

**업로드는 raw body 다.** 실측으로 확인했다 — 이 저장소에 `python-multipart` 가 없고
어디서도 멀티파트를 쓰지 않는다. `request.form()` 으로 파일을 받으려면 **6번째 의존성**이
생긴다. `Content-Type: application/octet-stream` 으로 바디를 그대로 읽으면 0 이다.

**⑦ 은 위험 구간이다.** zip 경로 순회(`../../etc/passwd`)와 zip bomb 이 여기서 터진다.
`zipfile` 로 풀 때 각 항목의 정규화된 경로가 대상 디렉터리 안에 있는지 확인하고,
압축 해제 후 총 크기 상한을 건다. **이건 테스트로 고정해야 하는 항목이다.**

**⑤ 가 이 절차의 핵심이다.** 다른 제품의 플러그인 설치는 대개 서명만 본다. 서명은 "누가
만들었나" 를 말할 뿐 "무엇을 하나" 를 말하지 않는다. 매니페스트와 내용을 대조하면 설치처가
읽는 문장(`[capabilities]`)이 실제 번들과 같음을 기계가 보증한다.

### 신뢰 키 목록

서명 검증에 쓸 공개 키를 어디 둘 것인가:
- `keys/plugin-trust/` 아래 공개 키 파일 — 기존 `keys/` 볼륨 관행과 같다
- 자체 서명 플러그인(설치처가 직접 만든 것)은 자기 키를 등록해서 쓴다
- **번들 안의 공개 키로 번들 안의 서명을 검증하면 안 된다** — 그건 서명이 아니다

## 7. active / inactive 의 정직한 의미

이 제품의 문서 규율은 "막는다" 와 "드러낸다" 를 구분해 적는 것이다(CRYPTO-4).
플러그인 토글도 같은 정직함이 필요하다.

| 등급 | inactive 가 실제로 뜻하는 것 | 활성화에 재시작이 필요한가 |
|---|---|---|
| **declarative** | 규칙·픽스처·패널이 로드되지 않는다. 완전히 없는 것과 같다 | 불필요 — 다음 요청부터 반영 |
| **external** | 호스트가 그 엔드포인트로 아무것도 안 보낸다. 완전히 없는 것과 같다 | 불필요 |
| **native** | 디스패치 지점에서 걸러진다. **그러나 모듈은 이미 임포트된 상태다** | **필요** |

**native 를 정직하게 적으면 이렇다.** 파이썬은 모듈을 안전하게 내릴 수 없다. `sys.modules` 에서
지워도 이미 만들어진 참조·등록된 콜백·몽키패치·시작된 스레드는 그대로 남는다. 그래서
"비활성화했으니 그 코드는 안 돈다" 는 native 등급에서 **참이 아니다.**

→ native 플러그인의 비활성화는 **"다음 재시작까지는 디스패치만 막는다"** 로 UI 에 표시해야
한다. 이걸 숨기면 사고 대응 중에 "껐는데 왜 돌지" 가 된다.

이건 설계 결함이 아니라 인프로세스 확장의 본질적 대가이고, 그래서 §4 가 native 를 예외로
다루는 이유이기도 하다.

## 8. 대시보드 통합

관제 UI 는 빌드 단계가 없다(`test_the_ui_is_served_without_a_build_step`). 플러그인 패널도
그 전제를 지켜야 한다.

```js
// static/app.js — 지금은 하드코딩된 목록이다
function tabsFor(session) {
  if (session.is_platform_admin) {
    tabs.push({ id: 'nodes', label: t('ui.nodes'), render: renderNodes }, ...);
  }
}
```

**플랫폼 관리자 탭에 `plugins` 를 하나 더한다** (관리 화면). 그리고 플러그인이 **자기 패널을
붙일 수 있게** 하려면 `tabsFor` 가 DB 에서 활성 패널 목록을 받아 합치는 형태가 된다.

패널 JS 를 어떻게 실행할 것인가가 UI 쪽 핵심 질문이다:

| 방식 | 격리 | 문제 |
|---|---|---|
| `<script>` 로 그냥 로드 | 없음 | 패널 하나가 세션 스토리지의 토큰을 읽는다. `test_the_token_is_kept_in_session_storage_only` 가 지키는 것이 무너진다 |
| `<iframe sandbox>` + `postMessage` | 브라우저 격리 | 호스트가 중계하는 데이터만 본다. 스타일 통일이 어렵다 |
| **패널을 선언형으로** (JS 없음) | 완전 | 표현력이 "어느 API 를 어떤 표로 그릴까" 까지 |

→ 첫 단계는 **선언형 패널**을 권한다. `panel.toml` 에 "이 엔드포인트를 이 컬럼으로 표로
그려라" 를 적는 형태다. 임의 JS 가 필요해지는 첫 사례가 나오면 그때 `iframe sandbox` 를 연다.
지금 JS 를 열면 되돌릴 수 없다.

## 9. 감사 · 격리 · 관측

이미 있는 장치를 그대로 재사용한다. 새로 만들 것이 거의 없다.

| 요구 | 재사용할 것 |
|---|---|
| 설치·활성·비활성·삭제가 감사에 남는다 | `store.audit()` 해시 사슬 (CRYPTO-4) |
| 플러그인 실패가 컨트롤 플레인을 안 죽인다 | `notify` 의 "죽은 채널이 호출자를 안 죽인다" + `blocking` 선언 |
| 느린 플러그인이 이벤트 루프를 안 막는다 | `notify._pool()` 오프로딩 |
| 나가는 페이로드에 원문이 없다 | `notify.redact()` |
| 에어갭에서 외부 플러그인이 막힌다 | `cluster.PERMANENT_REJECTIONS` |
| 플러그인 상태가 DB 에 있다 | `nodes` 테이블 패턴 (DB 가 YAML 을 이긴다) |
| 깨진 플러그인을 사람 말로 진단 | `cli.cmd_doctor` |
| 메트릭 | `observability.collect` 의 `gauge(...)` |
| 목록이 코드와 어긋나면 실패 | `test_feature_spec.py` · `test_meta.py` 패턴 |

메트릭 초안: `llmcc_plugins_installed` · `llmcc_plugins_active` · `llmcc_plugin_failures`
(플러그인 **id 라벨은 붙이되 테넌트 라벨은 절대 안 붙인다** — `test_metrics_never_label_by_tenant`).

## 10. 저장소 스키마 초안

`nodes` 테이블을 본보기로 한다 — 시드는 파일, 권위는 DB.

```sql
CREATE TABLE IF NOT EXISTS plugins (
    id             TEXT PRIMARY KEY,      -- 역DNS
    version        TEXT NOT NULL,
    tier           TEXT NOT NULL,         -- declarative | external | native
    manifest_json  TEXT NOT NULL,         -- 검증을 통과한 매니페스트 원본
    bundle_sha256  TEXT NOT NULL,         -- 디스크의 것과 대조한다
    signature_state TEXT NOT NULL,        -- signed | unsigned | invalid
    active         INTEGER NOT NULL DEFAULT 0,
    last_error     TEXT,                  -- 활성인데 로드 실패한 이유
    installed_by   TEXT,
    installed_at   REAL NOT NULL
);
```

`bundle_sha256` 이 있는 이유: 디스크의 플러그인 디렉터리를 누가 손으로 고쳤는지 `doctor` 가
잡을 수 있어야 한다. **감사 사슬이 DB 조작을 드러내는 것과 같은 방식으로**, 이 해시가
디스크 조작을 드러낸다. 막지는 못한다 — 그 한계도 같이 적어야 한다.

## 11. 결정이 필요한 것

이 탐색이 답하지 않은, 사람이 정해야 하는 것들이다.

| # | 질문 | 기울어진 쪽 | 왜 사람이 정해야 하나 |
|---|---|---|---|
| 1 | **native 등급을 열 것인가** | 1단계에서는 **닫는다** | 열면 §0 의 불변식이 플러그인에 대해서는 검사 밖으로 나간다. 프로바이더 확장 수요가 실제로 있는지가 관건 |
| 2 | 매니페스트 형식 | TOML | 신뢰하지 않는 입력이라는 성격 vs 저장소 YAML 관행 |
| 3 | 서명을 declarative 에도 강제할까 | 선택 | 강제하면 설치처가 자기 규칙 팩을 만들 때마다 키를 관리해야 한다 |
| 4 | 플러그인이 자기 DB 테이블을 가질 수 있나 | **못 가진다** | 가지면 마이그레이션·백업·파기·내보내기가 전부 플러그인을 알아야 한다. DATA-3·DATA-4 가 깨진다 |
| 5 | 테넌트가 플러그인을 켤 수 있나 | 1단계는 **플랫폼 전용** | 테넌트별 활성화는 격리 축이 하나 더 생기는 것이다 |
| 6 | 패널에 임의 JS 를 허용할까 | 1단계는 **선언형만** | 한 번 열면 못 닫는다 |
| 7 | 버전 업그레이드 시 이전 버전을 남기나 | 남긴다(롤백) | 디스크 사용량 vs 되돌릴 수 있음 |

## 13. 위험 등록부

| 위험 | 어디서 터지나 | 완화 |
|---|---|---|
| zip 경로 순회 · zip bomb | 설치 ⑦ | 정규화 경로 검사 + 해제 후 크기 상한. 테스트로 고정 |
| 정규식 파국적 백트래킹 | declarative 규칙 팩 | `Guard.validate_rule` 에 시간 상한 추가 |
| 플러그인이 이벤트 루프를 막음 | external 호출 | `blocking` 선언 + 오프로딩 (notify 패턴) |
| 매니페스트와 내용 불일치 | 설치 ⑤ | 대조 검사 |
| 비활성인데 도는 native 코드 | 활성화 토글 | UI 에 "재시작 전까지 디스패치만 차단" 을 표시 |
| 디스크의 플러그인 파일 변조 | 설치 후 | `bundle_sha256` 대조를 `doctor` 가 수행 |
| 에어갭에서 외부로 나가는 플러그인 | external 등급 | `[capabilities].network` 를 에어갭 판정에 연결 |
| 플러그인이 원문을 봄 | 페이로드 설계 | `redact()` 재사용 + `reads_prompt` 를 native 로 제한 |

## 14. 다음 단계 — 무엇부터 만들어 위험을 줄일까

탐색을 코드로 확인해야 할 순서다. **큰 것부터가 아니라 되돌리기 어려운 것부터.**

1. **포맷과 검증만 먼저** — 번들을 만들고(`zip`), 서명하고, 검증하는 왕복. UI 도 DB 도 없이
   함수 하나. 여기서 서명·매니페스트·경로 순회 방어가 실제로 되는지 확인한다
2. **declarative 한 종류만 끝까지** — 가드 규칙 팩 하나를 설치→활성→규칙이 실제로 마스킹까지
   가는 경로. 가장 수요가 크고 가장 안전한 등급이다
3. **DB 스키마와 감사** — `plugins` 테이블 + 설치/활성/비활성이 해시 사슬에 남는지
4. **대시보드 관리 화면** — 목록·설치·토글. 패널 확장은 아직 안 한다
5. **external 등급** — `notify` 채널을 이 틀 위로 옮기는 것이 첫 사례가 된다(기존 기능이므로
   회귀로 검증된다)
6. **native 는 §11-1 이 결정되기 전까지 열지 않는다**

각 단계는 이 저장소의 관행대로 **"끄면 실패하는" 회귀 테스트**를 함께 만든다.

## 15. 하지 말아야 할 것

- **런타임 `pip install`** — 도는 서버가 자기 의존성 그래프를 바꾸면 "이 설치본이 무엇을
  임포트하는가" 에 답할 수 없게 된다
- **플러그인에 `store` 객체를 그대로 넘기기** — `_scoped_where()` 우회 경로가 즉시 생긴다.
  넘긴다면 테넌트가 이미 박힌 좁은 뷰여야 한다
- **플러그인이 `create_job` · `response=` 쓰기에 닿게 하기** — 파이프라인·스케줄러 초크포인트가
  무너진다
- **매니페스트를 신뢰하고 검사하지 않기** — 매니페스트는 플러그인 저자가 쓴 문장이다
- **비활성화가 실제로 무엇을 막는지 얼버무리기** — native 는 재시작 전까지 완전히 안 꺼진다
- **첫 버전에서 등급을 안 나누기** — 나중에 나누는 것은 이미 설치된 플러그인의 계약을 깨는 일이다
