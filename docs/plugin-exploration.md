# 플러그인 시스템 기술 탐색

**상태: 탐색 결과. 아직 결정이 아니다.** 판정은 [design-decisions.md](design-decisions.md) 에서 내리고,
구현된 기능은 [feature-spec.md](feature-spec.md) 가 적는다.

요구: 플러그인을 **패키지로 개발**해서 **설치**하고, **관리자 대시보드에서 관리**하며
**active/inactive** 를 토글한다. **플러그인이 LLM 을 쓸 때는 이 제품의 API 프로토콜을 지난다** —
시스템 안쪽에서 LLM 에 직접 붙지 않는다.

마지막 문장이 이 설계의 전부를 바꾼다. 그것부터 적는다.

---

## 0. 결론 — 플러그인은 새 권한 모델이 아니라 **서비스**다

플러그인이 `POST /v1/generate` 로 앞문을 지난다면, 플러그인은 **소비자**다. 그리고 이 제품에는
소비자를 다루는 완성된 모델이 이미 있다.

```
플러그인  =  services 행 하나  +  서비스 토큰 하나  +  프로그램 하나
```

`services` 테이블을 보면 플러그인 관리에 필요한 것이 이미 다 있다.

```sql
CREATE TABLE services (
    id                   TEXT PRIMARY KEY,
    tenant_id            TEXT NOT NULL,
    name                 TEXT NOT NULL,
    allow_roles_json     TEXT NOT NULL DEFAULT '["*"]',   -- 이 플러그인이 쓸 수 있는 역할
    rate_limit_per_min   INTEGER,                          -- 폭주 상한
    budget_usd_per_month REAL,                             -- 비용 상한
    require_end_user     INTEGER NOT NULL DEFAULT 0,
    end_user_rate_limit  INTEGER,
    status               TEXT NOT NULL DEFAULT 'active',   -- active / inactive
    created_at           REAL NOT NULL
);
```

그리고 그 `status` 는 이미 **초크포인트에서 강제되고 있다.**

```python
# app/pipeline.py:157 — 잡이 만들어지기 전, 제출 경로의 단 한 곳
service = self._store.get_service(principal.scope(), principal.service_id)
if service is None or service["status"] != "active":
    raise ApiError("unauthorized", status=401)
```

**플러그인을 inactive 로 만든다 = 그 서비스의 LLM 접근이 즉시 끊긴다.** 새로 만들 필요가 없다.

> **다만 지금은 그 스위치를 켜고 끄는 경로가 없다.** `grep -rn "UPDATE services" app/` 결과가
> 비어 있다. `status` 는 생성 시점에 박히고 그 뒤로 아무도 못 바꾼다. 스키마와 강제는 있는데
> **손잡이가 없는 잠긴 스위치**다. 플러그인 작업의 첫 조각은 이 손잡이를 다는 것이다.

## 1. 앞문으로 지나면 공짜로 따라오는 것

플러그인이 `/v1/generate` 를 쓴다는 한 문장이 아래를 전부 해결한다. 이건 새로 설계하는 것이
아니라 **이미 있고 테스트로 고정된 기능들**이다.

| 플러그인에 필요한 것 | 이미 있는 기능 | 고정하는 테스트 |
|---|---|---|
| 플러그인이 보내는 프롬프트에서 PII 를 거른다 | GUARD-1 · GUARD-3 | `test_guard_runs_before_the_job_row_exists` |
| 플러그인이 경계 밖으로 원문을 못 낸다 | GUARD-5 · CLUSTER-3 | `test_internal_only_role_never_lands_outside` |
| 플러그인이 폭주해도 다른 소비자를 안 굶긴다 | AUTH-3 3단 레이트리밋 | `test_tenant_ceiling_cannot_be_bypassed_with_more_services` |
| 플러그인이 예산을 못 넘긴다 | CLUSTER-6 · CLUSTER-7 | `test_reservations_count_against_the_budget` |
| 플러그인이 쓸 수 있는 역할을 제한한다 | AUTH-6 `allow_roles` | `test_allow_roles_gate` |
| 플러그인별 사용량·비용이 보인다 | OPS-10 (`USAGE_AXES` 에 `service_id`) | `test_usage_and_spend_are_scoped` |
| 플러그인이 남의 테넌트를 못 본다 | DATA-1 | `test_no_unscoped_query_path_is_exposed` |
| 플러그인 활동이 감사에 남는다 | CRYPTO-4 | `test_editing_a_row_is_detected` |
| 토큰 회전·폐기 | AUTH-2 | `test_rotation_grace_window_keeps_old_alive` |

### 특히 중요한 것 하나

**플러그인은 마스킹본 응답만 받는다.** 출력 검사(GUARD-10)를 지난 뒤의 응답이 소비자에게
가고, 원문 응답 열람은 `GET /v1/admin/jobs/{id}/raw` 라는 **별도 권한 · 별도 감사 경로**다
(CRYPTO-6). 서비스 토큰으로는 그 경로가 안 열린다.

즉 **플러그인은 자기가 보낸 프롬프트의 원문조차 되읽을 수 없다.** 앞문 모델의 가장 큰 이득이다.

## 2. 앞선 탐색에서 무엇이 바뀌었나

이 문서의 이전 판은 **플러그인이 시스템 내부에서 돌면서 LLM 에 직접 붙는** 모델을 가정했고,
그래서 다음을 핵심 위험으로 잡았다.

> 이 제품의 불변식은 `tests/test_architecture.py` 가 `app/` 을 정적 분석해서 강제한다
> (`SOURCES = APP.rglob("*.py")`). 플러그인은 정의상 그 밖이라 인프로세스로 로드하면
> 스코프 우회 금지 · 잡 생성 초크포인트 · 응답 쓰기 초크포인트가 그 코드에 적용되지 않는다.

**이 위험은 앞문 모델에서 사라진다.** 플러그인이 `store` 도 `pipeline` 도 임포트하지 않고
HTTP 만 쓰면, 우회할 초크포인트에 애초에 닿지 못한다.

바뀐 것을 정리하면:

| | 이전 가정 (내부 직결) | 지금 (앞문 경유) |
|---|---|---|
| 권한 모델 | `[capabilities]` 를 새로 발명 | **`services` 행이 곧 권한** |
| 원문 접근 | 막을 방법을 설계해야 함 | 구조적으로 불가 |
| 등급 나누기 | declarative / external / native 3등급 필요 | **1등급이면 된다** |
| 인프로세스 파이썬 | 열지 말지가 최대 쟁점 | 플러그인의 문제가 아님 (§9 참고) |
| 남는 문제 | 격리 | **실행·수명주기·재귀** |

문제가 **보안 격리에서 프로세스 운영으로** 옮겨 갔다. 훨씬 다루기 쉬운 자리다.

## 3. 그래서 남는 진짜 질문 넷

### 3-1. 프로그램은 어디서 도는가

| 안 | 컨트롤 플레인의 역할 | 장점 | 대가 |
|---|---|---|---|
| **A. 서브프로세스로 띄운다** | 설치 · 기동 · 감시 · 종료 | "설치했더니 돈다" 가 성립 | 프로세스 감독 코드가 새로 필요. 런타임(파이썬) 전제 |
| **B. 별도 컨테이너** | 등록 · 토큰 발급 · 상태 표시만 | 격리 최상. k8s 친화 | 운영자가 컨테이너를 따로 올려야 함. "설치" 감각이 약함 |
| **C. 컨트롤 플레인이 이벤트마다 HTTP 호출** | 이벤트 라우팅 | `notify` 웹훅과 같은 모델. 검증된 패턴 | 플러그인이 상주 서버여야 함 |
| **D. 플러그인이 스스로 폴링** | **토큰 발급소 + 카탈로그** | 가장 단순. 컨트롤 플레인이 아무것도 안 함 | 설치·토글이 사실상 토큰 관리일 뿐 |

**기울어진 쪽: A 를 기본으로, B 를 옵션으로.** 사용자가 말한 "패키지로 개발해서 설치" 는
A 를 뜻한다. 다만 매니페스트에 실행 형태를 선언하게 해서 B·C 도 같은 카탈로그·같은 토글로
관리되게 한다.

**A 의 숨은 비용**: 이 저장소에는 지금 `subprocess` 사용처가 **하나도 없다**
(`grep -rn 'subprocess' app/` 이 빈다). 프로세스 감독은 새 영역이다 — 기동 실패 · 좀비 ·
재시작 폭주(crash loop) · 로그 수집 · 종료 대기가 전부 새로 설계할 것이다.
스케줄러의 `stop()` 이 실행 중 잡을 기다리는 패턴(`test_stop_does_not_hang_forever_on_a_stuck_job`)이
가장 가까운 선례다.

### 3-2. 무엇이 플러그인을 깨우는가

| 트리거 | 이미 있는 것 | 비고 |
|---|---|---|
| 상주(daemon) | — | 플러그인이 알아서 돈다. 컨트롤 플레인은 살았는지만 본다 |
| 스케줄 | — | 새로 필요. 스케줄러 루프에 얹으면 됨 |
| **이벤트** | `notify` 이벤트 버스 | `node_offline` · `budget_warn` · `budget_exhausted` · `guard_blocks_spike` · `model_ready` · `classifier_error_rate` 등이 이미 발화한다 |
| 잡 완료 | `completion.py:CompletionSignal` | 지금은 같은 프로세스 안에서만 동작 (SCHED-7) |
| HTTP | — | 컨트롤 플레인이 `/v1/plugins/{id}/...` 로 프록시할지 결정 필요 |

**이벤트 트리거는 거의 공짜다.** `notify` 가 이미 채널 목록에 이벤트를 뿌리고 있고,
`redact()` 가 나가는 페이로드에서 프롬프트와 비밀을 벗긴다. 플러그인을 채널의 한 종류로
보면 새 배관이 거의 없다.

### 3-3. 재귀 — 이 모델에서 **새로 생기는** 문제

플러그인이 `/v1/generate` 를 부른다 → 잡이 완료된다 → 완료 이벤트가 플러그인을 깨운다 →
플러그인이 다시 `/v1/generate` 를 부른다. **무한 루프이고, 예산이 다 탈 때까지 안 멈춘다.**

이전 모델(내부 직결)에는 없던 위험이다. 앞문을 쓰기 때문에 생긴다.

막는 법 후보:
- 잡에 **출처 표식**을 박는다 (`origin_service_id`). 플러그인이 만든 잡의 완료 이벤트는
  그 플러그인에게 보내지 않는다 — 가장 단순하고 확실
- **깊이 상한** — 잡이 잡을 낳은 횟수를 세고 상한을 건다. 체인이 정당한 경우(L2 선언적 체인)를
  살리려면 이쪽
- 서비스 예산(`budget_usd_per_month`)이 **최후의 방어선**이다. 이미 있다. 다만 그때는 이미
  돈이 나간 뒤다

→ 첫 번째(출처 표식)를 기본으로, 예산을 백스톱으로 두는 것이 맞다. **이건 반드시 테스트로
고정해야 하는 항목이다** — "플러그인이 만든 잡의 완료가 그 플러그인을 다시 깨우지 않는다".

### 3-4. 플러그인은 어느 테넌트에 속하는가

| 안 | 뜻 | 문제 |
|---|---|---|
| 플랫폼 테넌트의 서비스 | 설치처 전체가 공유하는 플러그인 | 테넌트별 데이터를 다루면 격리가 플러그인 코드 책임이 된다 |
| 테넌트마다 인스턴스 | 테넌트별로 켜고 끈다 | 같은 번들이 N개 서비스로 설치된다. 관리 화면이 복잡해짐 |
| 둘 다 (매니페스트가 선언) | `scope = "platform" \| "tenant"` | 1단계에 넣기엔 과함 |

**기울어진 쪽: 1단계는 플랫폼 테넌트 전용.** bootstrap 이 이미 `_platform` 테넌트에
`console` 서비스를 만들고 있으므로 자리는 있다. 테넌트별 인스턴스는 첫 수요가 생길 때.

## 4. 패키지 포맷

### 왜 wheel / `pip install` 이 아닌가

1. **에어갭** — `pip` 은 기본이 네트워크다 (PKG-4)
2. **의존성 5개 원칙** — 플러그인 의존성이 호스트 그래프에 섞이면 "이 설치본이 무엇을
   임포트하는가" 에 `pyproject.toml` 로 답할 수 없게 된다
3. **되돌리기** — `pip` 에는 비활성 개념이 없다. 우리에게 필요한 것은 제거가 아니라 토글이다
4. **이미지 불변성** — 도는 서버가 자기 venv 를 바꾸는 것은 `Dockerfile`·`compose.yml` 전제와 충돌

**앞문 모델에서는 이유가 하나 더 는다.** 플러그인은 호스트와 같은 파이썬 프로세스에서 돌 필요가
없으므로, 호스트의 venv 에 넣을 이유 자체가 없다.

### 번들 구조

```
acme-daily-digest-1.0.0.lccp          ← 그냥 zip 이다
├── plugin.toml                        매니페스트
├── SIGNATURE                          Ed25519 detached (선택 또는 필수 — §8)
├── main.py                            진입점 (subprocess 실행형인 경우)
├── requirements.txt                   플러그인 자기 의존성 (자기 venv 에만)
└── panel.toml                         대시보드 패널 선언 (선택)
```

**서명·검증에 새 의존성이 0 이다.** `cryptography>=42` 가 이미 의존성이고 Ed25519 를 지원한다.
`zipfile` · `hashlib` · `tomllib` 은 stdlib(3.11). 실측으로 확인했다.

### 매니페스트 — 권한 절이 서비스 필드로 그대로 간다

```toml
[plugin]
id            = "acme.daily-digest"
name          = "일일 요약 발송"
version       = "1.0.0"
requires_host = ">=0.2,<0.3"
description   = "매일 아침 전날 사용량을 요약해 메일로 보낸다"

[service]                          # ← 이 절이 그대로 create_service() 인자가 된다
allow_roles          = ["summarize"]      # 이 역할 밖은 호출조차 안 된다 (AUTH-6)
rate_limit_per_min   = 10                 # AUTH-3
budget_usd_per_month = 5.0                # CLUSTER-6·7

[run]
kind     = "schedule"              # daemon | schedule | event | external
schedule = "0 8 * * *"
entry    = "main.py"
runtime  = "python3.11"

[egress]                           # 앞문 밖으로 나가는 것. 에어갭 판정 대상
hosts = ["smtp.acme.internal"]

[panel]                            # 선택 — 대시보드에 붙을 화면
title    = "일일 요약"
endpoint = "/v1/admin/usage"
```

**핵심 설계**: `[service]` 는 새로 만든 권한 어휘가 아니라 **`create_service()` 의 인자 이름
그대로**다. 관리자가 설치 화면에서 읽는 문장과 DB 에 들어가는 값과 런타임에 강제되는 것이
같은 것이다. 권한 모델을 발명하지 않는다는 뜻이 이것이다.

### 매니페스트를 TOML 로 할까 YAML 로 할까

`config/` 는 전부 YAML 이지만 그건 **운영자가 직접 쓰는 파일**이다. 플러그인 매니페스트는
**남이 준 파일**이라 신뢰 수준이 다르다. `tomllib` 은 읽기 전용 stdlib 파서라 앵커·별칭·태그가
없고 공격 표면이 작다. → TOML 쪽으로 기운다. 다만 결정 사항이다(§8).

## 5. 설치 절차

```
① 업로드      POST /v1/platform/plugins        body = 번들 바이트 (플랫폼 관리자)
② 형식 검증    zip 인가 · plugin.toml 이 있는가 · 크기 상한
③ 서명 검증    SIGNATURE ↔ keys/plugin-trust/ 의 공개 키
④ 매니페스트   id 형식 · requires_host 범위 · [run].kind 별 필수 필드
⑤ 내용 대조    [run].entry 가 실재하는가 · [panel].endpoint 가 실재하는 라우트인가
⑥ 권한 표시    [service] 절과 [egress] 를 화면에 찍고 관리자 확인
⑦ 풀기        plugins/<id>/<version>/   ← zip 경로 순회 · zip bomb 방어
⑧ 서비스 생성  create_service(플랫폼 스코프, id, name, **manifest["service"])
⑨ 토큰 발급    issue_token(...)  → 플러그인 설정에 주입. 원값은 이때 한 번만
⑩ DB 등록      plugins 행. 상태 = installed, **inactive**
⑪ 감사        admin_audit 해시 사슬
───────────────────────────────────────────
⑫ 활성화(별도) POST /v1/platform/plugins/{id}/activate
```

**⑧⑨ 가 이 절차의 심장이다.** 설치가 곧 서비스 등록이므로, 그 순간부터 플러그인은 이 제품이
이미 아는 종류의 것이 된다. 사용량 화면에 서비스 축으로 잡히고, 레이트리밋에 걸리고,
예산에 계산된다 — 아무 배선 없이.

**업로드는 raw body 다.** 실측으로 확인했다 — `python-multipart` 가 없고 어디서도 멀티파트를
안 쓴다. `request.form()` 을 쓰면 **6번째 의존성**이 생긴다. `application/octet-stream` 으로
바디를 그대로 읽으면 0 이다.

**⑦ 은 위험 구간이다.** zip 경로 순회(`../../etc/passwd`)와 zip bomb 이 여기서 터진다.
해제 전 정규화 경로 검사 + 해제 후 총 크기 상한. **테스트로 고정할 항목이다.**

**토큰 주입 방법**은 결정 사항이다. 환경변수가 표준이지만(`channels_from_env` 선례), 프로세스
목록에 노출되지 않게 해야 한다. 파일로 떨구고 권한을 좁히는 쪽이 안전하다 —
`bootstrap` 이 마스터 키를 다루는 방식과 같은 고민이다.

## 5-b. 인식 — 무엇을 보고 "플러그인이 있다" 고 아는가

설치보다 이쪽이 더 결정적이다. "인식" 은 하나가 아니라 **서로 다른 질문 넷**이고,
각각 다른 시점에 다른 곳에서 답한다.

| 층 | 답하는 질문 | 언제 | 근거가 되는 것 |
|---|---|---|---|
| ① 파일 | 이 바이트 뭉치가 플러그인인가 | 업로드 순간 | zip 헤더 + 루트에 `plugin.toml` 이 있는가 |
| ② 매니페스트 | 무엇을 하는 플러그인인가 | 설치 검증 | `plugin.toml` 파싱 · 필수 필드 · `requires_host` |
| ③ 레지스트리 | **이 설치본에 무엇이 깔려 있나** | 기동 · 매 조회 | `plugins` 테이블 |
| ④ 역방향 | 플러그인이 호스트를 어떻게 아나 | 플러그인 런타임 | `GET /v1/meta` |

### ③ 이 권위다 — 파일이 아니라 DB

노드와 정확히 같은 모델을 쓴다. `cluster._load_declarations()` 를 보면:

```python
def _load_declarations(self) -> list[Node]:
    """DB 에 저장된 노드 선언. **읽기 실패가 기동을 막지 않는다.**

    노드 한 줄이 깨졌다고 컨트롤 플레인이 안 뜨면 그 줄을 고칠 방법도 없어진다.
    """
    rows = self._store.list_nodes()      # ← 디스크가 아니라 DB 를 읽는다
    for row in rows:
        try:    found.append(node_from_dict(name, row))
        except ConfigError:  continue    # ← 깨진 하나가 나머지를 막지 않는다
```

플러그인 인식도 이래야 한다.

- **디스크 스캔을 인식의 근거로 삼지 않는다.** 스캔이 권위면 파일 하나가 지워졌을 때
  플러그인이 조용히 사라지고, 활성 상태를 파일에 둘 방법도 없다
- 디스크는 **payload 일 뿐**이다. `plugins` 행이 "이 id 의 이 버전이 저기 있다" 를 말하고,
  `bundle_sha256` 이 디스크가 그 뒤로 변조되지 않았음을 대조한다
- **깨진 플러그인 하나가 기동을 막지 않는다.** 건너뛰고 `last_error` 에 이유를 적는다 —
  안 그러면 고칠 방법이 같이 사라진다

### 어디에 풀리나 — `config/` 는 못 쓴다

```yaml
# compose.yml
volumes:
  - lcc-data:/data              # 쓰기 가능
  - ./config:/app/config:ro     # ← 읽기 전용
```

`config/` 는 **읽기 전용 마운트**다. 주석도 그렇게 적혀 있다 — "런타임 변경은 관제 UI 를
통해 DB 로 간다. 제품에서 YAML 편집 후 재기동은 성립하지 않는다."

그리고 `cli_paths.bundled()` 은 **번들 자산**(휠에 담겨 배포되는 것)을 찾는 함수라
플러그인에는 안 맞는다. 플러그인은 런타임 설치물이므로 **데이터 디렉터리**를 따른다.

```
$LCC_DATA_DIR/                     기본값은 <repo>/data, 컨테이너에서는 /data
├── controlcenter.db
└── plugins/
    └── acme.daily-digest/
        └── 1.0.0/                 ← 번들을 푼 것
            ├── plugin.toml
            └── main.py
```

버전을 경로에 넣는 이유는 업그레이드 롤백 때문이다. 새 버전을 옆에 풀고 `plugins` 행의
버전만 바꾸면 되돌리기가 파일 이동이 아니라 행 갱신이 된다.

### ④ 는 이미 있다 — 플러그인은 `/v1/meta` 로 호스트를 인식한다

플러그인용 introspection API 를 새로 만들 필요가 없다. META-1 이 **토큰마다 다른 계약**을
이미 생성한다.

```
GET /v1/meta   (플러그인 토큰)
→ 이 토큰이 쓸 수 있는 역할 · 각 역할의 한도 · 오류 코드 · 엔드포인트
```

플러그인은 기동할 때 이걸 한 번 부르면 자기가 무엇을 할 수 있는지 안다. 역할 이름을
하드코딩하지 않아도 되고, 관리자가 `allow_roles` 를 줄이면 플러그인이 그것을 읽을 수 있다.
`test_meta_endpoint_is_generated_per_token` 과 `test_roles_endpoint_lists_only_allowed_roles`
가 이미 이 성질을 고정하고 있다.

### 설치 경로는 셋, 인식은 하나

| 경로 | 쓰는 곳 | 인식되는 방식 |
|---|---|---|
| 대시보드 업로드 | 평시 | 검증 → 풀기 → `plugins` INSERT |
| CLI (`python -m app plugin install <file>`) | 에어갭 · 자동화 | 같은 함수를 부른다 |
| `$LCC_DATA_DIR/plugins/` 에 파일 두기 | 이미지에 미리 넣기 · 복구 | 기동 때 **발견하되 자동 활성화하지 않는다** |

세 번째가 노드의 YAML 시드와 같은 자리다. 파일을 두면 "설치됨 · inactive" 로 DB 에 올라오고,
켜는 것은 여전히 사람의 별도 결정이다(§5 의 ⑫). **파일을 떨궜다고 코드가 도는 시스템은
만들지 않는다** — 백업 복원이 곧 재활성화가 되어 버린다.

세 경로가 전부 **같은 설치 함수**를 지나야 한다. 다른 경로가 다른 검증을 받으면 약한 쪽이
곧 우회로가 된다.

## 5-c. 실제 서버의 어디에 놓이나

배포 형태마다 다르다. 이 저장소는 **이 차이로 이미 한 번 깨진 적이 있다** —
`cli_paths.py` 독스트링에 그 기록이 있다("`pip install .` 로 설치한 것은 기동조차 못 했다").

### 형태별 경로 (실측)

| 배포 형태 | 플러그인 경로 | 근거 |
|---|---|---|
| **Docker / compose** (문서화된 운영 형태) | 컨테이너 `/data/plugins/<id>/<version>/` | `Dockerfile`: `ENV LCC_DATA_DIR=/data` · `VOLUME ["/data","/keys"]` |
| 저장소 체크아웃 (개발) | `<repo>/data/plugins/...` | `DEFAULT_DATA_DIR = ROOT/"data"`, `ROOT` = 저장소 루트 |
| `pip install` + systemd | `$LCC_DATA_DIR/plugins/...` — **반드시 지정해야 한다** | 미지정 시 `<site-packages>/data` 로 떨어진다 |

호스트에서 본 도커 경로는 **네임드 볼륨**이다. `compose.yml` 의 `name: llm-controlcenter` +
`volumes: lcc-data` 이므로:

```
/var/lib/docker/volumes/llm-controlcenter_lcc-data/_data/plugins/<id>/<version>/
```

컨테이너는 uid 10001 (`llmcc`) 로 돈다. `Dockerfile` 이 `/data` 를 그 uid 로 chown 하므로
하위 디렉터리는 그냥 만들면 된다.

> **휠 설치 형태의 기본값은 잘못됐다.** `LCC_DATA_DIR` 을 안 주면 데이터가
> `<site-packages>/data` 로 간다 — 흔히 root 소유이고, 업그레이드하면 날아간다.
> `deployment.md` 는 도커 형태만 다루므로 이 값이 문서에 없다. 플러그인과 무관하게
> 짚어 둘 것이고, 플러그인이 들어오면 **파일이 사라지는 방식으로** 문제가 커진다.

### 놓을 수 없는 곳들 — 이유가 각각 다르다

| 후보 | 왜 안 되나 |
|---|---|
| `/app/config/` | compose 가 **읽기 전용**으로 마운트한다 (`./config:/app/config:ro`) |
| `/app/app/` (패키지 옆) | 이미지 레이어다. 컨테이너를 다시 만들면 사라진다 |
| `/keys/` | KEK 전용이고 **백업 볼륨과 일부러 분리된 곳**이다. 플러그인을 거기 두면 그 분리의 의미가 없어진다 |
| `<site-packages>/` | 업그레이드가 곧 삭제다 |

### 디렉터리는 하나로 부족하다 — 셋으로 나눈다

```
/data/plugins/<id>/<version>/     ① 설치본 — 컨트롤 플레인만 쓴다
/data/plugins/_bundles/<id>-<version>.lccp
                                  ② 원본 번들 보관 — 복원·재설치·해시 대조용
/plugins-inbox/                   ③ 반입함 — 운영자가 파일을 떨구는 곳 (bind, ro)
```

**③ 을 ① 과 분리하는 이유.** 네임드 볼륨은 호스트에서 파일을 떨구기 불편하다. 에어갭에서
"파일 복사로 설치"(§5-b 세 번째 경로)를 쓰려면 bind 마운트가 필요한데, **설치본 디렉터리
자체를 bind 로 열면 안 된다** — 운영자가 푼 내용을 직접 고칠 수 있게 되고 그러면
`bundle_sha256` 대조가 상시 실패한다. 반입함은 읽기 전용으로 붙이고, 거기 있는 번들은
**같은 설치 함수를 지나** ① 로 들어간다.

```yaml
# compose.yml 에 더할 것
volumes:
  - lcc-data:/data
  - ./plugins-inbox:/plugins-inbox:ro     # 운영자가 .lccp 를 여기 떨군다
```

### 백업이 플러그인을 안 담는다 — 실측

`app/backup.py:snapshot()` 은 `sqlite3.backup` 으로 **DB 만** 뜬다. 디스크의 플러그인
payload 는 백업에 없다. 그대로 두면 복원 후 이렇게 된다.

> `plugins` 행은 살아났는데 `/data/plugins/<id>/<version>/` 에 파일이 없다.

이건 DATA-6 이 지키는 원칙("백업에 암호문·KEK 미포함")과 충돌하지 않는다 — 플러그인 번들은
비밀이 아니다. 선택지는 셋이고 결정이 필요하다(§8).

| 안 | 대가 |
|---|---|
| (a) 백업에 payload 를 포함 | 백업이 커진다. DB 스냅샷 하나라는 단순함이 깨진다 |
| (b) 복원 후 재설치 · `doctor` 가 짚어 준다 | 복원이 한 단계 늘어난다 |
| (c) 원본 번들(②)만 따로 보관하고 복원 절차가 그것으로 되푼다 | ② 를 유지해야 한다 |

**(b)+(c) 가 이 제품 결에 맞다.** `bundle_sha256` 이 이미 대조 수단이므로 `doctor` 가
"행은 있는데 파일이 없다 / 해시가 다르다" 를 사람 말로 짚고, ② 에서 되푸는 것을 안내한다.
`doctor` 가 복구 지시를 하고 그 지시가 실제로 복구시키는 것은 이 저장소의 확립된 패턴이다
(`test_doctor_recovery_instruction_actually_recovers`).

## 6. active / inactive 의 두 층

앞문 모델에서 토글은 **두 개의 서로 다른 것**을 뜻하고, 둘 다 필요하다.

| 층 | 끄면 무슨 일이 | 어디서 강제되나 | 지금 있나 |
|---|---|---|---|
| **① 서비스 (LLM 접근)** | 플러그인이 `/v1/generate` 를 불러도 401 | `pipeline.py:157` | 강제는 **있음**. 바꾸는 경로가 **없음** |
| **② 프로세스 (실행)** | 플러그인 프로그램이 안 돈다 | 새로 만들 것 | 없음 |

**둘을 나누는 것이 중요하다.** ①만 끄면 플러그인은 계속 돌면서 401 을 받는다 — 로그가
시끄럽지만 **안전 상태로 멈춘다.** ②만 끄면 프로세스는 죽었는데 토큰은 살아 있다.

권장: **끌 때는 ① 먼저, 켤 때는 ② 먼저.** 어느 순간에도 "토큰은 살아 있는데 감시받지 않는
프로세스" 상태가 없게 한다.

그리고 이전 판이 걱정하던 "파이썬은 모듈을 못 내린다" 문제는 **여기서 사라진다.** 플러그인이
별도 프로세스이므로 끄는 것은 프로세스를 죽이는 것이고, 그건 확실하다.

## 7. 대시보드

플러그인 관리 화면은 **기존 서비스 화면 위에 얹힌다.** `static/app.js:tabsFor` 의 플랫폼
관리자 탭에 `plugins` 를 더한다.

보여줄 것:
- 목록 — 이름 · 버전 · 서명 상태 · 서비스 활성 · 프로세스 상태 · 마지막 오류
- **소비 현황** — `GET /v1/admin/usage?group_by=service_id` 가 이미 준다. 새 API 가 필요 없다
- 설치(파일) · 토글 · 삭제 · 토큰 회전

**패널 확장(플러그인이 자기 화면을 붙이는 것)은 별개 문제이고 더 위험하다.** 관제 UI 는 빌드
단계가 없고(`test_the_ui_is_served_without_a_build_step`), 토큰을 세션 스토리지에만 둔다
(`test_the_token_is_kept_in_session_storage_only`). 플러그인 JS 를 `<script>` 로 그냥 로드하면
그 패널이 관리자 토큰을 읽는다.

→ 1단계는 **선언형 패널만** (`panel.toml` 이 "이 엔드포인트를 이 컬럼으로 표로 그려라"를 적는다).
임의 JS 가 필요한 첫 사례가 나오면 `<iframe sandbox>` + `postMessage` 를 연다. 지금 열면 못 닫는다.

| 7 | 플러그인이 자기 DB 테이블을 갖나 | **못 갖는다.** 가지면 백업·파기·내보내기가 플러그인을 알아야 한다 |
| 8 | 패널에 임의 JS 를 허용할까 | 1단계 **선언형만** |
| 9 | 플러그인이 관리 API(`/v1/admin/*`)를 쓸 수 있나 | **1단계는 못 쓴다.** 쓰게 하려면 토큰이 관리자 등급이어야 하는데 그건 등급이 다른 이야기다 |
| 10 | 플러그인 payload 를 백업에 담나 | **안 담는다.** 원본 번들을 보관하고 `doctor` 가 되푸는 것을 안내 (§5-c) |

## 9. 이 문서가 다루지 않는 것 — 프로바이더 확장

"새 LLM 백엔드 종류를 더하는 것"(예: vLLM 전용 어댑터, 사내 추론 서버)은 **플러그인이 아니다.**
프로바이더는 앞문의 *바깥쪽* 이고, 노드 호출 경로 한가운데서 도는 인프로세스 코드다.

`app/providers/base.py` 에 이미 레지스트리가 있다 (`register` · `build_provider` ·
`known_providers`). 이걸 외부에 여는 것은 별개 축이고, 열면 이전 판이 지적한 문제가
그대로 돌아온다 — `tests/test_architecture.py` 가 `app/` 만 훑으므로 외부 프로바이더 코드에는
초크포인트 검사가 적용되지 않는다.

**두 축을 섞지 말 것.** 플러그인(앞문 소비자)과 프로바이더 확장(내부 어댑터)은 위험도가
다르고 따라서 절차도 달라야 한다.

## 10. 위험 등록부

| 위험 | 어디서 터지나 | 완화 |
|---|---|---|
| **재귀 호출로 예산 소진** | 이벤트 트리거 | 출처 표식 + 예산 백스톱. **회귀 테스트 필수** |
| zip 경로 순회 · zip bomb | 설치 ⑦ | 정규화 경로 검사 + 해제 후 크기 상한 |
| 플러그인 크래시 루프 | 프로세스 감독 | 재시작 백오프. `scheduler` 의 지터 패턴 재사용 |
| 토큰 유출 | ⑨ 주입 | 파일 + 권한 좁히기. 프로세스 목록·로그에 안 남기 |
| 플러그인이 데이터를 밖으로 보냄 | `[egress]` | 에어갭 판정에 연결. 앞문은 지켰어도 **송신은 별개** |
| 좀비 프로세스 | 종료 경로 | `stop()` 대기 + 강제 종료 상한 |
| 서비스는 살았는데 프로세스가 죽음 | 토글 순서 | 끌 때 ① 먼저, 켤 때 ② 먼저 (§6) |
| 플러그인 로그에 프롬프트가 남음 | 플러그인 코드 | 호스트가 통제 못 함. **문서로 경고 + 로그 수집 시 마스킹** |

## 11. 다음 단계

되돌리기 어려운 것부터. 각 단계는 이 저장소 관행대로 **"끄면 실패하는" 회귀 테스트**를 만든다.

1. **잠긴 스위치를 연다** — `services.status` 를 바꾸는 스토어 메서드 + `/v1/admin/services/{id}`
   PATCH. 지금 없어서 못 쓰는 기능을 쓰게 만드는 것이고, **플러그인과 무관하게 그 자체로 결함
   수정이다.** 테스트: inactive 서비스의 토큰으로 제출하면 401
2. **번들 왕복** — 만들고 · 서명하고 · 검증하고 · 안전하게 푸는 함수들. UI 도 DB 도 없이.
   경로 순회와 zip bomb 방어를 여기서 고정
3. **설치가 서비스를 만든다** — ⑧⑨ 배선. 매니페스트 `[service]` → `create_service` →
   토큰 발급. 이 시점에 플러그인은 아직 안 돌지만 **사용량 화면에 이미 잡힌다**
4. **재귀 방지** — 출처 표식 + "플러그인이 만든 잡의 완료가 그 플러그인을 다시 안 깨운다" 테스트.
   실행을 붙이기 **전에** 넣어야 한다
5. **실행 하나만** — `[run].kind = "schedule"` 하나. daemon 과 event 는 그 다음
6. **관리 화면** — 목록 · 설치 · 토글. 패널 확장은 아직
7. **첫 실제 플러그인** — `notify` 채널 하나를 이 틀 위로 옮기면 기존 기능이라 회귀로 검증된다

## 12. 하지 말아야 할 것

- **플러그인에게 내부 객체(`store` · `pipeline`)를 넘기기** — 앞문 모델의 이점이 그 순간 사라진다
- **런타임 `pip install`** — 호스트 의존성 그래프가 오염된다. 플러그인 의존성은 플러그인 venv 에
- **재귀 방지 없이 이벤트 트리거를 켜기** — 예산이 다 탈 때까지 안 멈춘다
- **플러그인 토큰에 관리자 등급 주기** — 앞문을 지난다는 전제가 무의미해진다
- **`services.status` 를 안 고치고 플러그인 토글을 따로 만들기** — 강제 지점이 두 개가 되고
  둘은 반드시 어긋난다
- **패널에 임의 JS 를 먼저 열기** — 되돌릴 수 없다
- **플러그인과 프로바이더 확장을 한 기능으로 묶기** — 위험도가 다르다 (§9)
