# 런북 — 마스터 KEK 유출 대응

이 문서는 **압박 속에서 읽는 문서**입니다. 설명은 뒤로 빼고 할 일을 앞에 둡니다.

전제: 마스터 KEK 가 유출됐거나 유출이 의심됩니다. 예를 들어 키 파일이 백업과 같은
곳으로 흘러갔거나, `LCC_PROMPT_KEY` 가 로그·CI 아티팩트에 찍혔거나, 키를 알던 사람이
떠났습니다.

---

## 지금 할 일

```sh
lcc doctor                 # 1. 현재 상태 확인
lcc rotate-kek             # 2. 회전
# 3. 워커 재기동 (새 키를 읽게)
lcc doctor                 # 4. 확인
```

회전은 **저장된 암호문을 재암호화하지 않습니다.** 테넌트 수만큼의 행 갱신으로
끝나므로 원문이 몇 기가바이트든 초 단위입니다. 이유는 아래 "왜 빠른가" 에 있습니다.

---

## 무엇이 위험하고 무엇이 아닌가

먼저 이것부터 판단하세요. 대응 범위가 달라집니다.

| 유출된 것 | 공격자가 원문을 읽을 수 있나 | 대응 |
|---|---|---|
| **KEK 만** (DB 는 안전) | **아니오.** DEK 는 DB 안에 있고 그것 없이는 아무것도 못 엽니다 | 회전. 회전 뒤 옛 KEK 는 무용지물입니다 |
| **KEK + DB 사본** | **예.** 이미 읽혔다고 가정하세요 | 회전은 *앞으로*를 막을 뿐입니다. 침해 신고·영향 범위 산정이 본체입니다 |
| **DB 만** (KEK 는 안전) | 아니오 | 회전 불필요. 다만 마스킹본은 평문이므로 그 범위는 별도 판단 |

**두 번째 칸이면 회전은 대응의 시작이지 끝이 아닙니다.** 백업 저장소에 KEK 를 같이
두지 말라는 규칙(`deployment.md`)이 존재하는 이유가 정확히 이 칸입니다.

---

## 절차

### 1. 상태 확인

```sh
lcc doctor
```

`KEK 검증 OK — 테넌트 N개의 DEK 를 모두 풉니다` 가 나와야 합니다.

**여기서 이미 실패하면 회전하지 마세요.** 회전은 고장을 고치는 도구가 아니고, 못 여는
테넌트가 있는 채로 회전하면 그 테넌트는 영영 못 엽니다. 올바른 KEK 를 먼저 찾으세요.
(`rotate-kek` 도 같은 이유로 이 경우 스스로 거절합니다.)

### 2. 회전

```sh
lcc rotate-kek
```

새 키를 직접 발급해 넣으려면(시크릿 매니저를 쓰는 경우):

```sh
LCC_PROMPT_KEY_NEW="$(vault read -field=key secret/lcc/kek-2026)" lcc rotate-kek
```

> **새 키를 명령줄 인자로 받지 않습니다.** `argv` 는 같은 호스트의 다른 사용자에게
> `ps` 로 보이고 셸 히스토리에도 남습니다.

키를 안 주면 새로 만들어 **한 번만** 표시합니다. 그 자리에서 보관처로 옮기세요.
부트스트랩이 마스터 KEK 를 1회만 표시하는 것과 같은 규칙입니다.

명령이 끝나면 키 디렉터리는 이렇게 됩니다:

```
keys/master.key                    ← 새 키 (서비스가 읽는 것)
keys/master.key.rotated-1767225600 ← 옛 키 (아직 지우지 마세요)
```

### 3. 워커 재기동

**도는 프로세스는 기동 시점의 키를 메모리에 들고 있습니다.** 재기동하지 않으면
그 워커들은 옛 키로 새 래핑을 풀려다 실패합니다.

```sh
docker compose restart      # 또는 설치처의 재기동 방법
```

`LCC_PROMPT_KEY` 환경 변수로 키를 넣는 구성이라면 **그 값도 함께 바꿔야 합니다** —
회전은 파일을 갱신하지만 남의 환경 변수까지 고치지는 못합니다.

### 4. 확인

```sh
lcc doctor
```

그리고 관제 UI 에서 원문 열람이 실제로 되는지 한 건 확인하세요. 진단은 DEK 래핑까지만
보고, 암호문 자체는 안 열어 봅니다.

### 5. 옛 키 파기

**4번이 통과한 뒤에** 하세요.

```sh
shred -u keys/master.key.rotated-1767225600
```

회전이 끝난 순간부터 옛 키는 아무것도 못 엽니다. 그래도 자동으로 지우지 않는 이유는,
서비스가 실제로 도는 것을 확인하기 전까지 되돌릴 길을 남겨야 하기 때문입니다.

옛 키를 **백업 저장소에서도** 지우세요. 백업에 옛 키가 남아 있으면 유출된 키가 살아
있는 것과 같습니다 — 다만 그 백업의 DB 스냅샷은 옛 래핑이므로, 그 백업으로 복원할
계획이 있다면 옛 키를 지우기 전에 그 백업부터 새 키로 다시 뜨세요.

## 중단된 회전

`doctor` 가 이렇게 말하면 회전이 중간에 끊긴 것입니다:

```
! KEK 회전이 파일 교체 직전에 중단됐습니다: keys/master.key.new
```

**어느 쪽이 사실인지 추측하지 마세요 — `doctor` 가 이미 판정해서 알려 줍니다.**
DB 를 실제로 열어 보고 두 메시지 중 하나를 냅니다:

| doctor 가 말하는 것 | 뜻 | 할 일 |
|---|---|---|
| "DB 는 이미 **새 키**로 감싸여 있습니다" | 커밋은 됐고 파일 교체만 안 됐습니다 | `mv keys/master.key.new keys/master.key` |
| "DB 는 아직 **현재 키**로 감싸여 있습니다" | 커밋 전에 끊겼습니다 | `rm keys/master.key.new` 후 다시 `rotate-kek` |

둘을 바꿔서 하면 **어떤 키로도 못 여는 상태**가 됩니다. 그래서 이 판단을 사람에게
맡기지 않습니다.

### 왜 이런 창이 있나

DB 커밋과 키 파일 교체는 서로 다른 저장소에 대한 쓰기라서, 둘을 한 트랜잭션으로 묶을
방법이 없습니다. 없앨 수 없는 창이므로 **그 창에서 두 키가 모두 디스크에 있도록**
순서를 짰습니다(`app/keyrotation.py`). 어디서 죽어도 복구할 수 있고, 남아 있는
`master.key.new` 자체가 중단의 증거입니다.

> "디스크에 있다" 는 **말 그대로**입니다. 새 키는 `fsync` 로 굳힌 뒤에야 DB 를
> 커밋하고, 파일 이름 변경도 디렉터리 `fsync` 로 굳힙니다. 페이지 캐시에만 있으면
> 프로세스 죽음에는 살아남지만 정전에는 사라지고, 그 사이 DB 는 새 래핑을 들고
> 남습니다 — 그러면 어떤 키로도 못 여는 상태가 됩니다.

## 되돌리기

4번 확인이 실패하고 원인을 모르겠다면 옛 키로 되돌아갈 수 있습니다. **단 옛 키를 아직
안 지웠을 때만** 가능합니다.

```sh
mv keys/master.key           keys/master.key.failed
mv keys/master.key.rotated-* keys/master.key
```

그런데 이것만으로는 부족합니다 — DB 는 이미 새 키로 감싸여 있습니다. 옛 키로 되돌리려면
**새 키를 옛 키로 다시 회전**해야 합니다:

```sh
# 새 키가 아직 master.key 인 상태에서
LCC_PROMPT_KEY_NEW="$(cat keys/master.key.rotated-1767225600)" lcc rotate-kek
```

유출 대응 중이라면 이것은 유출된 키로 돌아가는 것임을 기억하세요. 되돌리기는
"회전이 뭔가를 깨뜨렸다" 가 확실할 때의 임시 조치입니다.

---

## 왜 빠른가 — 회전이 실제로 바꾸는 것

```
프롬프트 원문 ──[테넌트 DEK 로 봉인]──> jobs.prompt_cipher   ← 안 바뀝니다
테넌트 DEK   ──[마스터 KEK 로 래핑]──> tenants.dek_wrapped   ← 이것만 바뀝니다
```

KEK 를 바꾼다는 것은 **DEK 의 포장지를 바꾸는 것**이지 안에 든 것을 바꾸는 것이
아닙니다. DEK 자체는 그대로이므로 그 DEK 로 봉인된 암호문은 전부 그대로 열립니다.

이 사실이 대응 속도를 가릅니다. 몰랐다면 "수억 건의 프롬프트를 재암호화해야 하나" 를
유출 상황에서 따지게 되고, 그것이 이 문서가 존재하는 이유입니다.

---

## DEK 는 회전하지 않습니다

의도적으로 **없는 기능**입니다. 근거:

- **DEK 는 평문으로 프로세스 밖에 나가지 않습니다.** 그러므로 DEK 만 유출되는 경로가
  없습니다 — DEK 가 샜다면 KEK 도 샌 것이고, 그때는 위 표의 두 번째 칸입니다.
- **KEK 만 샜다면 re-wrap 으로 충분합니다.** 공격자는 DB 를 못 가졌으므로 DEK 에
  닿을 수 없고, 회전 뒤 옛 KEK 는 아무것도 못 엽니다.
- **KEK + DB 가 샜다면 DEK 를 바꿔도 이미 읽힌 것을 되돌리지 못합니다.** 공격자는
  암호문 사본을 오프라인으로 들고 있습니다.

DEK 를 바꾸면 그 테넌트의 **기존 암호문이 전부 못 열리게 됩니다**(crypto-shredding).
그것이 필요한 상황은 "이 테넌트의 보관 원문을 지운다" 이고, 그 경로는 이미 있습니다 —
테넌트 파기(`purged_at` + `dek_wrapped = NULL`). 같은 일을 하는 두 번째 명령을 만들면
둘 중 하나는 언젠가 잘못된 상황에서 불립니다.

보관 원문의 수명을 짧게 하고 싶다면 회전이 아니라 `raw_prompt_retention_days`
(기본 7일)를 줄이세요.
